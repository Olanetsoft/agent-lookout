# Architecture

Agent Lookout has two halves and a shared middle. The collector is Node code that asks each agent tool for its sessions every two seconds and keeps the latest answer in memory. The dashboard is a React page that polls the collector over a local HTTP API and draws what comes back. Both use the session model in `src/core/`.

## The session model

`src/core/sessions/session.ts` defines the types that adapters produce and the dashboard consumes.

A `Session` has a stable `id`, the `source` it came from, the `surface` it runs in, a `name`, a working directory, a `status`, and the times it started and last changed status. The surface is `terminal`, `vscode`, `desktop`, `cloud`, `browser` or `unknown`. The Claude Code and Codex adapters report the first three, and `unknown` when they cannot tell, and so does the status-file adapter from a file's `app`. `surfaceLabel` names each but `unknown`, which has no name: the dashboard, an email and a post leave an app that is not known out, and the Sessions list shows a dash for it. A source whose sessions belong to many agents, as status files do, also gives each session an `agent`: the agent's own name, in plain text.

A session can also carry a `lastWriteAt`: when its agent last wrote to the file the adapter reads it from, which is that file's own modified time. Codex's adapter and the status-file adapter give it, and Claude Code's does not, because its registry file is not rewritten as the session works: it can stay hours old while a session is busy. A time that `plausibleTime` does not believe, or that is earlier than the session's start or a status file's own `since`, is left out. It is a measurement and decides nothing in the collector: no status, no event and no notification depends on it.

A session whose folder is in a git repository carries a `git`: `{ branch }` for the branch checked out, or `{ commit }`, the first seven characters of the commit's ID, when no branch is, and with either a `repository`, `{ id, name }`: the repository the folder belongs to, the same for every worktree of it. The collector adds it to the sessions of every source alike, as [Git branches](#git-branches) describes.

A session the collector can take you to itself also carries a `jump`. That is `{ kind: "tmux", place }` for a session whose process runs in a tmux pane, where `place` is the tmux session, window and pane in words, such as `work:2.1`, or `{ kind: "terminal", app, place }` for one whose process runs in a tab of Terminal or iTerm2, where `app` and `place` are both the app's name. It is there to be read. It holds nothing a command could be made of: the pane's own ID and the tab's terminal never leave the collector.

Every tool's own states map onto six statuses: `needs-you`, `working`, `idle`, `finished`, `failed` and `unknown`. A tool may report only some of them: Codex sessions are never `needs-you` or `failed`. A session that needs you also carries a `waitingReason` of `permission`, `question` or `other`, and the vendor's own wording in `waitingDetail`. A session that has been idle for 24 hours or more has `stale` set. The time of a session's last status change must not move while it goes on needing you, because a later time on a session that is still waiting is read as a new wait.

Each poll produces a `SessionsSnapshot`: the sessions, and a `SourceHealth` for each adapter that says whether it is `ok`, `searching`, `unavailable`, `not-set-up` or in `error`, with a plain-language detail, a list of what the adapter reads and runs, and, for a source read in more than one way, its `basis`: the way this answer was read. It also carries `capabilities`: what the source's agent can report at all, as yes, no or partly for working and idle, needs you, finished, failed, names, Jump and quiet for, with one short reason for each no and partly. Each adapter declares its own once, the poller puts them on every health of that source, the Sources view draws its table from them, and a test holds the table in the guide to them. `not-set-up` is for a source that has nothing to read until the person sets it up, such as a folder of status files nobody has made. Like `unavailable`, it is not a problem, and outside the Sources view the dashboard does not mention it.

The poller compares each source's sessions with the last list that source reported successfully in the same way of reading. Claude Code's adapter reads its registry alone while the claude command fails, and Codex's reads its session files without the folder of locks while that cannot be listed, so each of those has a `basis` of its own and is never compared with an answer read the other way. A session that appeared, changed status or ended becomes a `SessionEvent`. A change to `needs-you` is a warning, a change to `failed` is critical, and the rest are advisory. The first successful poll is the baseline and produces no events, because the sessions in it were already running. A source that is `not-set-up` has been read too, and holds no sessions, so the sessions in a folder of status files made later appear. Each poll also appends a `HistoryPoint` with the counts per status. Its idle count leaves out stale sessions, as the Idle count on the Overview does, so the chart behind that count ends at its figure. The Last hour chart and the history charts behind the Overview's counts draw these points, and the Timeline, the Waited on you bars and the Events log use the points to tell the time that was measured from the time that was not.

Fields can be added to these types. Existing fields are never renamed or removed.

## The collector

An adapter implements the interface in `src/collector/adapters/adapter.ts`: an `id`, a `label` and a `poll()` that resolves to a health report and a list of sessions. `poll()` never throws. A failure goes into the health report.

The poller in `src/collector/poller.ts` calls every adapter every two seconds and skips a beat when the previous poll is still running. An adapter that has not answered within 15 seconds is reported as an error until it does. Events and history sit in bounded in-memory buffers: the last 1,000 events and the last 10,800 history points, which is six hours. Both are lost when the process stops. A poll in which no source answered adds no history point, so the gap is not drawn as zero. Nor does a poll in which a source that answered before fails to answer, for as long as it keeps failing, so the charts never draw a total that leaves its sessions out. A source that turns `unavailable` or `not-set-up` leaves a gap once and then counts as having no sessions.

Before it makes a snapshot, the poller hands every source's sessions to an `annotate` function it was given, which adds what no source knows itself: the collector's gives each session its git branch. The events are worked out from the sessions as their sources gave them, so a branch that changes is no event, and if `annotate` fails the sessions go as they are.

The poller hands each snapshot, as soon as it is the latest, to a listener it was given. Whatever the listener throws is dropped, so it cannot stop a poll.

`createCollector` in `src/collector/collector.ts` builds the three adapters, Claude Code's, Codex's and the one for status files, the poller, the two stores, the collector's own notifications, the email and webhook notifications when they are set up, the tmux pane finder, the Terminal and iTerm2 tab finder, the branch finder and the request handler in one call. Every host starts the collector that way.

## The API

One handler, in `src/collector/handler.ts`, answers every route. Every route returns JSON, and every route but one is a `GET` that only reads. The response shapes are in `src/core/api.ts`.

| Route                          | Returns                                                                                                                               |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------- |
| `/api/health`                  | `{ ok: true, version }`                                                                                                               |
| `/api/sessions`                | The latest `SessionsSnapshot`                                                                                                         |
| `/api/events?since=<epoch ms>` | `{ events }`, newest first, at most 200                                                                                               |
| `/api/history?windowMs=<n>`    | `{ points, startedAt }`, one point per poll, 15 minutes by default and six hours at most                                              |
| `/api/email`                   | `{ on, to, events, afterMs, problem, last, limitedUntil }`: whether email is set up, for which events, and how the last email went    |
| `/api/webhook`                 | `{ on, host, events, afterMs, problem, last, limitedUntil }`: whether a webhook is set up, its host alone, and how the last post went |
| `POST /api/jump`               | `{ ok: true, kind, place }` once the session's tmux pane is selected, with `app` too once its terminal tab is in front                |

`startedAt` is when the collector began. The dashboard marks the time before it as unmeasured instead of drawing zeros.

[API.md](API.md) describes each route, its answer and its checks for a program that reads them, and why the API has no token.

The handler refuses any request whose `Host` header is not `localhost`, `127.0.0.1` or `[::1]`, any request with an `Origin` header that is not one of those, and any request the browser marks as `Sec-Fetch-Site: cross-site`. It sends no CORS headers. This keeps other websites, and DNS rebinding, away from session names and paths.

A request may carry the header `X-Agent-Lookout-Notifications`. The dashboard sends it on every request, to say which events that page's notifications are on for: `off` for none, `on` for a wait alone, which is all it could say before the events could be chosen, and otherwise `on; events=` followed by the names, such as `on; events=needs-you,finished`. Any other value, a name that is not one of the four included, and a header sent twice, which Node joins with a comma, says nothing. `notificationsHeaderValue` and `readNotificationsHeader` in `src/core/api.ts` write and read it. It changes no answer. The handler reads it only after the checks above and the check that the request is a `GET`, and passes it to the collector's notifications, described under [Notifications from the collector](#notifications-from-the-collector). A page at another address cannot send it: a browser asks permission with a preflight before it sends a header of this kind across origins, and the handler refuses a preflight, with 403 from another site and 405 otherwise, and sends no CORS headers. The header's name is in `src/core/api.ts`.

### The route that acts

`POST /api/jump` selects the tmux pane a session runs in, or brings forward its tab of Terminal or iTerm2. It is the only route that changes anything, so `createJumpRoute` in `src/collector/jumpRoute.ts` makes checks of its own after the handler's. `jumpRefusalFor` refuses, before the body is read, anything but a `POST` (405, which is what a preflight gets when it comes from another port of this machine under the same name; one from another site has already been refused with 403 by the handler's own checks), a request with no `Origin` or one that is not loopback, a request the browser marks as anything but `same-origin`, a request without the header `X-Agent-Lookout-Action: jump` (all 403), a content type other than `application/json` (415) and a body said to be over 1,024 bytes (413). The body is then read up to that limit and must be exactly `{ "sessionId": "..." }` (400).

The route looks the session up in the poller's latest snapshot and, going by the kind of its `jump`, asks the pane finder for the pane it found for that session's process, or the tab finder for its tab. A session that is not listed, or has neither, is a 404. Nothing from the request goes further than that lookup. `selectPane` in `src/collector/tmux/selectPane.ts` then runs fixed tmux commands with the pane's ID: `select-window`, `select-pane`, `display-message -p` to learn the pane's session and place, `list-clients`, and `switch-client` for each client showing another session. The answer is 200 with the place, 409 when tmux says the pane has gone or has no server running, 500 when tmux could not be run, and 429 for a second jump within a second or while one is under way. After a 409 the finder is told to look again at the next poll.

For a tab, `focusTab` in `src/collector/terminal/focusTab.ts` builds the arguments with `focusTabArgs`: the app's fixed script, `TERMINAL_SCRIPT` or `ITERM_SCRIPT`, as `-e` lines, then `--` and the tab's terminal, which must be `/dev/ttys` and digits, or nothing is run. The script is aimed at the app by its bundle ID, returns `missing` without starting an app that is not running, finds the tab or iTerm2 session whose `tty` is the argument, selects it, brings its window forward, activates the app and returns `found`. `focusOutcomeOf` reads the run: `found` is 200 with the app, `missing` is 409 `tab-gone`, after which the tab finder forgets that process and looks again, macOS's error -1743 is 403 `not-allowed`, and anything else, a timeout included, is 500. osascript gets a minute, since the first time macOS holds the run until the person answers its question, and no other jump is made meanwhile.

A 404, 409, 429 or 500, and the 403 for `not-allowed`, carries a `reason`, which the dashboard turns into its own words. The 403s of the checks above carry none.

## The Claude Code adapter

The adapter lives in `src/collector/adapters/claude-code/`. It reads sessions from two places.

The first is the session registry: the folder `~/.claude/sessions`, where Claude Code keeps one small file for each running session, named `<pid>.json`. The adapter reads it on every poll. Reading it starts no process. The format is undocumented, so every field is optional and a malformed file is skipped. A name must end in `.json` to be read and a link is not followed, so the `.key` files in the same folder are never opened.

The second is `claude agents --json --all`, the listing command that Claude Code documents for outside tools. The adapter runs it on the first poll and every 30 seconds after that, and keeps the answer until the next run. Each run starts Claude Code's own program, which costs CPU and may contact Anthropic the way it does for anyone who runs it. That is why the command is run seldom.

The command's answer outranks the registry.

- It supplies the background jobs that are finished or failed and have no process left. The registry holds a file per live process and cannot.
- A registry session that the answer did not list is left out, unless it started too recently for the answer to have known about it.
- When the answer lists a running session the registry lacks, when a registry file has a status the mapping does not know, or when the folder cannot be read, sessions come from the command. It is then run every 5 seconds until the registry can be relied on again.

When the command cannot be found, or fails, the registry is used alone and the health detail says so. If the registry cannot be read either, the source is `unavailable` and the detail names where the adapter looked.

The adapter looks for the `claude` binary on `PATH`, then at `~/.local/bin/claude`, `/opt/homebrew/bin/claude`, `/usr/local/bin/claude`, `~/.npm-global/bin/claude` and `/usr/bin/claude`. The fixed locations are there because an app started from the Finder does not inherit the shell's `PATH`. The last two are for Linux, and come after the Mac's so that the order on a Mac is unchanged.

It starts the command directly, with no shell, with stdin closed and a five second timeout. Shell wrappers and hooks can print before or after the list, so the adapter takes the first JSON array on stdout that holds a session and ignores the rest. A Claude Code too old to know `--all` is asked without it, and its finished jobs are not listed.

A registry file can outlive a crashed session. The adapter checks that each process still exists with `process.kill(pid, 0)`. It also asks `ps` when the process started and compares that with the start time in the registry file, to catch a process ID that has since gone to another program. Two start times a minute apart or less are taken as one process's, because the `ps` of Linux works a start time out from the clock and prints another one after the clock is set. `createProcessStartCheck` in `src/collector/processes/processStart.ts` does this, and when any session's answer is due it asks about every session in that one run, so sessions that started at different times share one `ps` every 30 seconds.

`src/core/mapping/claudeCodeMapping.ts` holds the mapping. `busy` becomes `working`, `waiting` becomes `needs-you` and `idle` stays `idle`. The registry's `shell` is `working` too. A background session also has a `state`: `working` stays `working`, `blocked` becomes `needs-you`, `done` and `stopped` become `finished`, and `failed` stays `failed`. A live `busy` or `waiting` wins over the `state`. A live `idle` gives way to a `state` that says more. A value the mapping does not recognise becomes `unknown`. `waitingFor` gives the reason: `permission prompt` is `permission`, `input needed` is `question` and anything else is `other`.

A background job that is finished or failed, with no process left, stays in the list for 24 hours and is then left out. The 24 hours are counted from the moment the collector first saw the job over. For a job that was already over when the collector started, they are counted from its start time. `finishedJobs.ts` in the adapter's folder does this. Any other session that ends leaves the list, and the poller records an `ended` event for it.

A session in VS Code gets a `links.open` of `vscode://anthropic.claude-code/open?session=<sessionId>`. Other surfaces have no link.

A session that needs the person gets a `waitingText`, what it is asking, from the end of its transcript. The code is in `transcript/` in the adapter's folder. `waitingTexts.ts` runs after every poll over the sessions the poll found, and reads only those that need the person and whose id is a session id. `transcriptFile.ts` finds the transcript at `<claude home>/projects/<folder>/<sessionId>.jsonl`, where the folder is the session's folder with every character that is not a letter or a digit made a `-`, and otherwise lists `projects` and looks for the file in each folder in it. It opens the file with `openRegularFile`, so a link, a pipe or a folder is never read, and reads at most its last 256 KB, by position. `lastAsk.ts` drops the first line of that tail unless the tail is the whole file, skips any line that does not parse and every subagent's line, `isSidechain`, and finds the newest `tool_use` of an assistant line with no `tool_result` after it in a user line, and no prompt or later reply after it. Of the tools one message asks for, it takes the first still waiting, even when a later one has its result. A line with no `message.id` cannot be matched to its message, so any later assistant line then ends the wait. That tool use becomes one line: the first question and how many more for `AskUserQuestion`, `Run:` and the command's first line for Bash, `Edit:`, `Write:` or `Read:` and the file relative to the session's folder, `Fetch:` and the address, `Search:` and the words, "Approve the plan" for `ExitPlanMode`, nothing for `Task` or `Agent`, which start a subagent, and `Use:` and the name for any other tool. It is made one line and cut to 200 characters by `waitingText` in `src/core/text.ts`. Anything unexpected gives no text. A wait's file is found once, while its status time stands, and its end is read again only when the file's size, modified time or identity has changed. Everything remembered of a session is dropped on the first poll it is not waiting. The poller keeps its baselines, and `sessionChanges` its memory, without the text, and no event, history point, email or webhook post holds it. `AGENT_LOOKOUT_WAITING_TEXT=off` stops any transcript being opened, and the source's facts say so.

A live session whose process runs inside a tmux pane gets a `jump`. The code is in `src/collector/tmux/`, and `createCollector` hands the adapter the same pane finder the jump route reads. On each poll the adapter gives the finder the process IDs of its live sessions, and the finder decides whether to look: when it first has a process to ask about, every 30 seconds after that, and sooner, though never within 5 seconds of the last look, when a process has turned up since. A look runs `tmux -u list-panes -a` with a fixed format of the pane's process, its ID, its window and pane numbers and its session's name, and, only when that lists a pane, `ps -A -o pid=,ppid=` once, with `readProcessParentsWithPs` in `src/collector/processes/processParents.ts`. `paneOfProcess` in `panes.ts` walks from a session's process up through its parents until one is a pane's process. tmux is found on `PATH`, then at `/opt/homebrew/bin/tmux`, `/usr/local/bin/tmux`, `/opt/local/bin/tmux` and `/usr/bin/tmux`, and is started with `execFile`, with no shell, stdin closed and a 2 second timeout. When there is no tmux, no server or no answer, no pane is known and the source's health is untouched. `AGENT_LOOKOUT_TMUX=off` stops tmux being run at all. An adapter built without a finder, as in most tests, looks for no pane.

A live session in no pane whose process runs in a tab of Terminal or iTerm2 gets a `jump` of kind `terminal`. The code is in `src/collector/terminal/`, and `createCollector` hands the adapter the same tab finder the jump route reads. The adapter gives it the same process IDs as the pane finder. A process keeps its terminal and its parents for as long as it runs, so `createTabFinder` in `tabFinder.ts` looks for each one once: a look runs `ps -A -o pid=,ppid=,tty=,comm=`, with `readProcessTableWithPs` in `src/collector/processes/processTable.ts`, once for every process that turned up since the last look, never within 5 seconds of it, and forgets a process that has gone. `tabOfProcess` in `terminalTabs.ts` takes the session's own terminal, which must be `ttys` and digits, then walks up through its parents until one is Terminal's executable, `/System/Applications/Utilities/Terminal.app/Contents/MacOS/Terminal`, iTerm2's, `/Applications/iTerm.app/Contents/MacOS/iTerm2`, or the `iTermServer-` program iTerm2 runs its shells under from `~/Library/Application Support/iTerm2`. Every parent before the app must have the session's terminal: one with another, or none, made that terminal, so the session is in another app's terminal, such as Warp's, VS Code's or tmux's, and has no tab. The walk stops at a loop, at a missing parent and at the first process. `ps` is run only on macOS. `AGENT_LOOKOUT_TERMINAL_JUMP=off` stops the finder looking and the runner running.

The [guide](GUIDE.md#settings-you-can-change) lists the settings that change where the adapter looks. One of them needs a reason: when `AGENT_LOOKOUT_CLAUDE_HOME` replaces `~/.claude`, a `claude` found on the machine is not run, because it would list the sessions of the usual folder.

## The Codex adapter

The adapter lives in `src/collector/adapters/codex/`. [adapters/codex.md](adapters/codex.md) is its reference: every file it reads and how often, which sessions are listed, the full status table, the Codex version it was checked against and what breaks when Codex changes.

Codex documents no way to list its sessions that works without starting Codex's own server, which writes to its folder, or without editing its config to add hooks. So the adapter reads files alone and runs no program. Nothing it reads is documented.

Each poll lists the day folders for today and yesterday under `sessions/` and reads the `rollout-*.jsonl` files in them. From each file it reads the first `session_meta` line, for the session's folder, start time and source, and the last line that says a turn started or ended. After that it reads only what was appended. It lists `thread-writer-locks/`, where Codex keeps a lock for each session a Codex process has open, and never opens those files. It reads `session_index.jsonl` for the names people give sessions. `io.ts` opens only ordinary files, never a link or a pipe, and `rolloutFile.ts` bounds every read.

`src/core/mapping/codexMapping.ts` maps the last turn line and the lock to a status. A turn under way is `working`, a turn that is over is `idle`, and a session whose lock has gone is `finished`. Codex does not write approval waits to these files, so a Codex session is never `needs-you`: one that is waiting for approval is in a turn that has started, and shows as `working`. Codex older than 0.155 keeps no locks, so a session it created is never `finished`. The health detail states each limit when it applies.

The Codex folder is `AGENT_LOOKOUT_CODEX_HOME` if set, then Codex's own `CODEX_HOME`, then `~/.codex`. When it is missing, the source is `unavailable`, and the adapter looks for it again once a minute with one `stat`. Polls in between touch nothing. A folder named by `AGENT_LOOKOUT_CODEX_HOME` that holds no `sessions/` is an answer instead: the source is `ok` with no sessions.

A session's id is `codex:<thread id>`. A Codex session has no process ID and no link, so it has no Jump button. Its `lastWriteAt` is the modified time from the `lstat` the adapter makes of the file on each poll, before deciding whether to read it, so no read is added for it. It also counts the files of subagents the session started, whose `session_meta` names it in `parent_thread_id`, because a session waiting on its subagents writes nothing to its own file while they work. A subagent's own subagents are not counted.

## The status-file adapter

The adapter lives in `src/collector/adapters/status-files/`. It is how an agent Agent Lookout has no adapter for appears, including one a person wrote: the agent writes one small JSON file for each session into a folder, and the adapter reads the folder. The format is Agent Lookout's own, and the [guide](GUIDE.md#your-own-agents) is its reference.

The folder is `AGENT_LOOKOUT_STATUS_DIR` if set, otherwise `~/.agent-lookout/sessions`. The adapter never makes it and never writes in it. While it is not there the source is `not-set-up`, and its detail says in one sentence how to start. The folder is listed on every poll, so a folder made later is read at once. A folder that is there and cannot be listed is an `error`.

Each poll lists the folder and reads the files directly in it whose names end in `.json` and do not start with a dot, in order of name. It reads at most 200: when there are more, it finds when each was last written with `lstat`, which does not follow a link, and reads the 200 written most recently, so files that ended sessions left behind are skipped before a new session is. A file is opened with the Codex adapter's `openRegularFile`, so a symbolic link, a pipe or a folder is never read, and its size is checked before a byte is read: anything over 16 KB is not read. `statusFile.ts` parses a file and refuses one that is not a JSON object with `agent` and `status`. Every text is cleaned of control characters and of the characters that change the direction of text, and the names are cut to a length. So is a session name taken from the file's name. A file that is refused for any of these reasons is counted, the count is one of the source's facts, and the detail names the first such file and why.

`src/core/mapping/statusFileMapping.ts` holds the mapping: `working`, `idle`, `finished` and `failed` keep their names, `waiting` becomes `needs-you` with the reason `permission`, `question` or `other`, and any other word becomes `unknown`. `statusFileMapping.ts` also maps the file's `app`: `terminal`, `vscode` and `desktop` become the surface of that name, and anything else, or none, `unknown`. `toSession.ts` makes the session. Its id is `status-files:<file name>`, its `agent` is the file's own, its surface is the mapped `app`, and it has no start time, no link and no jump.

The rest is in `index.ts`:

- A file whose `pid` names a process that has gone is a leftover, and its session is not shown, unless it says it finished or failed: those are expected to have no process.
- A finished or failed session stays for 24 hours from its status time, or from when its file was last written, even while its process runs: the file says the session is over.
- The status time is the file's `since` when `plausibleTime` believes it. Without one, the adapter keeps the time it first saw the session in that status, and keeps it while the status stands, so a wait's time does not move. A session that was already in the folder at the adapter's first look has no such time.
- A file that was read a poll ago and cannot be parsed now was most likely caught half written. What it said a poll ago stands, for that one poll, so a session does not end and appear again between two polls.
- The session's `lastWriteAt` is the modified time of the file it was read from, from the open file, so an agent that writes its file as it works, or touches it, moves it on.

## Git branches

The code is in `src/collector/git/`. It reads files and runs nothing: no git, and no other program.

`findGitHead` in `branchFinder.ts` takes a session's folder and looks for `.git` in it and in each folder above it, with `lstat`, so a link named `.git` is not followed. The nearest `.git` of any kind ends the walk, as it does for git, so a repository further up is never shown in place of one that cannot be read. The walk never looks in the home folder or the root, nor above them, nor in more than 24 folders, and a folder that does not exist is in no repository. A `.git` folder holds `HEAD`. A `.git` file, as a worktree or a submodule has, names the git folder that holds it in one line, `gitdir: <path>`, relative to the folder the file is in unless it is a whole path. Beside a `HEAD` that a `.git` file leads to, `commondir` is read when it is there: a worktree's git folder has one, a line naming the repository's own git folder, git's common dir, relative to the folder it is in unless it is a whole path, and a submodule's has none. Every file is opened with the Codex adapter's `openRegularFile`, so a link, a pipe or a folder is never read, and each is read only when it is 4 KB or less and is UTF-8. `gitHead.ts` parses them: `ref: refs/heads/<branch>` gives the branch, cleaned of control characters and of the characters that change the direction of text and cut to 200 characters, and a commit's whole ID, 40 or 64 hexadecimal characters, gives its first seven. Anything else gives nothing, never a guess. No other file in a repository is read, `packed-refs`, the configuration and the index included.

`repository.ts` works out the repository from those paths, and reads nothing itself. A repository is its own git folder, git's common dir, which every worktree of it shares. `repositoryOf` takes the folder the `.git` was found in, the git folder that holds `HEAD`, and what that git folder's `commondir` names, if anything. A `.git` folder is its repository's own. A worktree's git folder, `<common>/worktrees/<name>`, belongs to the common dir its `commondir` names, which is `<repository>/.git` only for an ordinary clone: it is `storefront/.bare` for worktrees kept beside a bare repository, a folder anywhere for a repository made with `--separate-git-dir`, and `<repository>/.git/modules/<name>` for a submodule's worktrees, so the path alone would not tell. Any other `.git` file, such as a submodule's, names its repository's own git folder, so a submodule is a repository of its own, as a repository inside another's folder is. A `commondir` that is there but cannot be read gives no repository, and the branch still shows. The id is the first 16 hexadecimal characters of the SHA-256 of the common dir's path, so the dashboard can group by it without being sent a path that a session's own `cwd` does not already hold. The name is the folder's that holds `.git`, cleaned and cut as a branch is, and for a worktree is taken from the common dir: the folder that holds it when its name starts with a dot, as `.git` and `.bare` do, and otherwise its own name without a `.git` at the end, so `storefront.git` gives `storefront`. One that comes to no name, at the root, gives no repository. Where a repository's main folder and its git folder kept apart are named differently, its sessions can carry two names for one id, and `repositoryGroups` heads the group with the one first in order.

`createBranchFinder` keeps what it read for each session's folder for 10 seconds, so a folder's `HEAD` is read at most once in 10 seconds however many sessions work in that folder. Sessions in different folders of one repository each read it. It forgets a folder no session is in. It reads the folders one after another, and starts no read while one has not answered, so a read that hangs, as on a network drive that has gone away, holds one of the few threads Node reads files with, never all of them, and the collector's other reads go on. A poll waits at most a second for the reads it starts, and not for those an earlier poll started. Past that it goes on with what was read before, and the answers are used when they arrive. Until a hung read answers, no branch is read again, and a session that appears meanwhile shows none.

## Hosts

The same collector and the same dashboard are meant to run under more than one host. Three seams make that possible.

On the server side, the handler has a Node-style `(req, res)` signature and knows nothing about what mounts it. Three hosts mount it today. Two are in `src/collector/hosts/`, and the third is the Mac app, described under [The Mac app](#the-mac-app). `collectorPlugin.ts` mounts it inside Vite's server for `npm run dev` and `npm run preview`. `standalone.ts` is the standalone server: `runStandalone` serves the built files and the API on `127.0.0.1`, on port 4777 or `AGENT_LOOKOUT_PORT`, and stops on SIGINT or SIGTERM. It takes the folder of built files, the environment, where to print and the process to stop as arguments, so tests run it against a temporary folder. `serve.ts` is the entry that `npm start` runs, and calls it with `dist/` and this process's environment. `agent-lookout start`, in `src/cli/start/startCommand.ts`, calls it the same way, with the `dist/` beside `bin/`, puts `--port` in place of `AGENT_LOOKOUT_PORT`, and with `--open` hands the address to `openInBrowser` in `openBrowser.ts`, which runs `/usr/bin/open` on macOS or `xdg-open` on Linux with `spawn`, no shell and that one argument, in a session of its own so Ctrl+C does not reach the browser it starts, and only for a loopback address. `server.ts` and `staticFiles.ts` hold its HTTP server and its file handler. `AGENT_LOOKOUT_HOST` can move it to `::1`, and it refuses to bind to any address that is not loopback.

On the dashboard side, every request goes through `apiRequest(path, init)` in `src/dashboard/lib/api/apiHost.ts`. It has the shape of `fetch` and defaults to a same-origin request. It accepts only root-relative paths, so the dashboard cannot name another host. `setApiHost` replaces the transport, which is how a browser extension could supply the data without an HTTP server. That host does not exist yet. The Mac app needs no transport of its own: its page and its API are on one origin.

Notifications have a seam of the same kind. `notificationHost()` in `src/dashboard/lib/notifications/notificationHost.ts` says what the permission is, asks for it and shows a notification, and defaults to the browser's Notifications API. `setNotificationHost` replaces it, for a host whose page cannot use the browser's. The Mac app keeps the browser's, which Electron shows as the app's own.

The collector has its own, for the notifications it shows when no page is open. `SystemNotifier` in `src/collector/notifications/systemNotifier.ts` has one method, `show`, which never throws. `createCollector` takes one as `notifier` and defaults to `createSystemNotifier()`, which runs `osascript` on macOS and does nothing on any other system. The Mac app passes its own. Tests pass one that writes down what it was asked to show.

Email has a seam of the same kind. `EmailSender` in `src/collector/email/smtpSender.ts` has one method, `send`, which never rejects. `createCollector` takes a `createEmailSender`, which it calls only when email is set up, and defaults to `createSmtpSender`, which sends through the mail server in the environment. Tests pass one with short timeouts, aimed at a mail server of the test's own on `127.0.0.1`. The webhook has one too: `WebhookSender` in `src/collector/webhook/webhookSender.ts`, whose `send` never rejects either. `createCollector` takes a `createWebhookSender`, which it calls only when the webhook is set up, and defaults to `createHttpSender`. Tests pass one with a short timeout, aimed at a server of the test's own on `127.0.0.1` that writes down each request.

tmux is reached through one function too. `RunTmux` in `src/collector/tmux/program.ts` takes a list of arguments and resolves with what tmux printed or how it failed, and never rejects. `createCollector` takes one as `tmux` and defaults to `createTmuxRunner()`, which runs the tmux binary it finds. The pane finder and the jump route share it. Tests pass one that runs nothing, or one aimed at a tmux server of the test's own.

So are Terminal and iTerm2. `RunOsascript` in `src/collector/processes/osascript.ts` takes a list of arguments for `/usr/bin/osascript` and resolves with what it printed, or how it failed and whether it ran out of time, and never rejects. `createCollector` takes one as `osascript`, and defaults to `createOsascriptRunner()`, which runs it on macOS while `AGENT_LOOKOUT_TERMINAL_JUMP` is not `off`. It also takes `readProcesses`, which the tab finder reads the table of processes with and the pane finder each process's parent, and `readProcessStarts`, which the Claude Code adapter checks start times with. Both default to asking `ps`, through `runPs` in `src/collector/processes/ps.ts`, the one way the collector runs it. Tests pass an osascript that runs nothing and writes down its arguments, and a table of processes of their own, so no test drives a real terminal.

## The Mac app

The Mac app, in `src/desktop/`, is the third host. It is an Electron app whose main process builds the collector with `createCollector`, as the standalone server does, so it has every feature the server has. It opens no port.

Its one window loads the dashboard from an address scheme of the app's own, `agent-lookout://app/`, named in `src/core/appAddress.ts`. `main.ts` registers the scheme before the app is ready, as standard and secure, reachable by `fetch`, with CORS off, and answers it with `protocol.handle`. `protocol/appProtocol.ts` sends `/api/*` to the collector's handler and every other path to the static file handler the standalone server uses, so the built files are served by the same rules and with the same Content-Security-Policy. Any other host under the scheme has nothing, and a request that another origin made is refused before either handler sees it.

Both handlers are Node handlers, so `protocol/requestAdapter.ts` stands between them and Electron. It turns the Fetch `Request` Electron hands over into the shape of an `IncomingMessage`, with its body as a stream, collects what the handler writes into a `Response`, and drops the headers that describe a connection. The handler's own checks are not relaxed. The adapter gives every request the `Host` 127.0.0.1, since it came from this app's own window, and gives a request from the app's own page the `Origin` `http://127.0.0.1`. It takes the page's origin from Electron's `initiatorOrigin`, which the page cannot set, before the `Origin` header. A request from any other origin is given the `Origin` `null`, which no check accepts, so it never gets through. The dashboard's code does not change: its page is on the same origin as its API, so `apiRequest` stays a same-origin `fetch`.

The page runs in the sandbox, with context isolation, no Node and no preload. `navigation/links.ts` decides where it may go. The window shows the app's own addresses and nothing else. A link to an `https:` address, or to a Claude Code session in VS Code in the exact shape `CLAUDE_CODE_OPEN_LINK` in `src/core/mapping/claudeCodeMapping.ts` describes, is handed to `shell.openExternal`, and that is the only place an address from the page ever goes. Every other link is dropped, and no page may open a window. `navigation/windowRules.ts` applies those rules to every way the page could leave: a navigation, a redirect, a frame, a new window and a webview. `navigation/sessionRules.ts` lets the page show notifications and use no other permission, cancels every web request the window's session would make, so nothing the page does can leave the machine, and refuses downloads. Both import only types from Electron and take what they act on as an argument, so their tests hand them stand-ins for the page and its session and check each rule.

The packaged app will not start with `--remote-debugging-port` or `--remote-debugging-pipe`, which would let any program on this computer drive the page, Jump included: `process/launchSwitches.ts` names them, and `main.ts` quits before anything else when it finds one. The Electron fuses already shut out the Node debugger and `NODE_OPTIONS`. A development run keeps the switches. What the app would otherwise lose, an error in the main process and the collector's warnings, goes to its log, `main.log` in `~/Library/Logs/Agent Lookout/`, which `process/appLog.ts` writes and moves aside when it passes half a megabyte. A startup that fails says so in a message, with where the log is, and quits.

The page's own notifications are the browser's, which Electron shows as coming from the app. The collector's, for when the window is closed, come from `notifications/desktopNotifier.ts`, which shows them with Electron's `Notification` in place of `osascript`, so macOS files them under Agent Lookout as well, and a click on one opens the window.

One copy runs at a time. A second finds the first through `app.requestSingleInstanceLock`, which shows its window, and quits. Closing the window leaves the app and its collector running, clicking the Dock icon opens the window again, and quitting stops the collector. `window/mainWindow.ts` makes the window: no title bar, its three buttons on the rail's top cell, where `window/windowFrame.ts` places them by macOS's own measurements of them, a minimum size, and a background in the colour of the ground of the theme the page last showed, which the page says in `<meta name="theme-color">`. `window/windowState.ts` reads and writes `window-state.json` in the app's folder of user data: the window's place and size, and that colour. A page that fails to load is shown all the same after a few seconds, and one whose process dies is loaded again. In full screen, where macOS hides the window's buttons, the window marks `<html>` with `data-fullscreen`, a fixed line it runs in the page, and the rail drops their cell. A right-click offers Cut, Copy and Paste where they can be done, from `menu/contextMenu.ts`. `menu/appMenu.ts` has the menus a Mac app is expected to have, Settings… and a Help menu with the guide among them, with reload and the developer tools in development only. The collector tells `main.ts` each poll's sessions through `onSnapshot`, and `notifications/dockBadge.ts` puts the count that needs you on the Dock icon, by the rule that lights the lamp in the page.

The app updates itself, in `updates/`, and `updates/updater.ts` is the one small module the rest of the app knows: an `Updater` with `status`, `check`, `install`, `setAutomatic`, `start` and `stop`. electron-updater installs through Squirrel, which needs an app signed with a Developer ID, so until the app is signed it does the work itself, and a signed app can move to electron-updater behind the same interface. `release/endpoints.ts` names where to look: the latest release's `latest-mac.yml`, which electron-builder writes beside the zips, since `electron-builder.ts` gives it a `generic` provider, one it never uploads to, and which the release workflow attaches to the release. `release/releaseRequest.ts` makes the only requests the app sends off the machine, with Node's own HTTPS client in the main process: the page's session cancels every web request, and Electron's `net` goes through that session, so neither is used. Each address, the first and each a redirect leads to, must be `https:` on GitHub, `release-assets.githubusercontent.com` or `objects.githubusercontent.com`, and each request has a time limit, a size limit and a `User-Agent` of `Agent-Lookout/` and the version. `release/manifest.ts` reads the manifest, keeping a file only when its name, size and SHA-512 are what they can be, `release/version.ts` offers only a newer release that is not a prerelease, and `release/downloadCheck.ts` checks the zip's size and SHA-512 as it is written into a temporary folder of the updater's own. `install/bundleCheck.ts` unpacks it with `/usr/bin/ditto -x -k`, refuses a bundle, a `Contents` or an `Info.plist` that is a link, which ditto unpacks as a link, and checks that the bundle's `CFBundleIdentifier` is this app's and its `CFBundleShortVersionString` the version offered. `install/installLocation.ts` refuses, with a reason the page and the dialog give in the same words, to install where the app cannot change its own bundle: App Translocation, anything under `/Volumes/`, a disk image or another disk, or a folder it cannot write. Only Install and Restart starts `install/installHelper.ts`'s helper, `/bin/sh` with a fixed script that takes the process ID and three paths as arguments, waits for the app to quit, moves the old bundle aside, moves the new one in and opens it, and puts the old one back if the new one cannot be moved in. Before it starts the helper, the updater notes the version in `update-state.json`, and the copy that opens next, finding a version there that is not its own, says the install did not work and opens on the Updates card; an app that has not quit a minute after the helper stops waiting says so too. The daily check leaves that said, unless a newer version is out. A newer release with no zip for this kind of Mac is an answer, as a release with no Mac app is, and neither is logged or told of. The updater checks a short while after the app starts, if a day has passed since the last check, and then once a day while the switch is on, asking itself each hour whether a day has passed, which `updateSettings.ts` keeps in `update-state.json` with the switch, the last version the daily check told of and the version being installed. The notification of a version found says it is being downloaded, or, where it cannot be installed, to open Settings to see how. A development run checks only when asked and never installs. The page reaches the updater only through `/api/app/*` on the app's own scheme: `protocol/appProtocol.ts` sends those addresses to `updates/updateRoute.ts`, which gives the POSTs the checks the jump route makes, `actionRefusalFor` in `src/collector/jumpRoute.ts`, each with its own action, and the standalone server and the dev server never mount it. Check for Updates… in the app menu opens Settings on the Updates card, `#settings/updates`, when the window is open, and shows the answer in a dialog, from `updates/updateDialog.ts`, when it is not, one at a time: chosen again while that answer is on its way or shown, it does nothing.

The page knows it is in the app by its scheme. `lib/shell/appWindow.ts` marks `<html>` with `data-host="app"` before React renders, and the stylesheet then keeps the rail at its full width for the window's buttons, gives them a cell at its top, level with the header, and lets the header, that cell and the strip above the header move the window, while every control in them still takes its clicks. Settings draws its Updates card, `components/settings/UpdatesCard.tsx`, only there, and reaches the app's updates through `lib/updates/appUpdate.ts`, by `apiRequest` like everything else.

`scripts/build-desktop.mjs` bundles `main.ts` with esbuild into `dist-electron/main.cjs`, with every library in it, copies the built dashboard beside it and writes the app's own `package.json`. `electron-builder.ts` packs that folder into the app, signed ad hoc, as a disk image and a zip for Apple silicon and for Intel, with `latest-mac.yml` beside them, with no `node_modules` folder, with the Electron fuses that would let its code be run another way turned off, and with the sentence macOS shows when Jump first asks to bring forward a tab of Terminal or iTerm2. In the app, osascript runs as Agent Lookout's own child, so macOS asks about Agent Lookout itself, and `automationAskLine` in the dashboard says so. `.github/workflows/release-mac.yml` builds the same on a Mac runner for a pushed tag, with read access only, and a second job, the only one that can write, attaches the disk images, the zips and `latest-mac.yml` to the tag's release.

## The dashboard

`src/dashboard/App.tsx` puts a rail down the left edge and, beside it, the header over the current view. The rail, in `components/rail/Rail.tsx`, links to three views: Overview, Sources and Settings. Each view has its own address in the URL fragment, `#overview`, `#sources` or `#settings`, which `lib/shell/view.ts` reads, so the back button, a reload and a bookmark land on the same view. Choosing one replaces the view in `<main>` and moves focus there, and the rail and the header stay. A fault inside a view is caught there and leaves the rail and the header standing. A session's details open over the Overview at an address under it, `#overview/session/` and the session's ID, which `lib/shell/sessionDetails.ts` builds and reads. `components/panels/SessionPanel.tsx` draws them in the same dialog as the history charts, from what the page already holds, and asks the collector for nothing more.

The Overview holds the Needs you panel, the Last hour chart, the Sessions list, the Events log and the Timeline. It leaves out a tool that was not found, unless none was, so someone who uses one tool sees what they would if only that one were watched. The Sources view shows each source's health and the facts it reports about what it reads and runs. Settings holds the theme, the choice of whether to be notified and of what, and whether email and a webhook are set up and for what, which it only reads. On every view, `useShortcuts` in `hooks/shell/useShortcuts.ts` listens for the keys that `shortcutFor` in `lib/shell/shortcuts.ts` names. `/`, and Cmd+K or Ctrl+K, open `SearchDialog` in `components/keyboard/`, which finds sessions with `searchSessions` in `lib/sessions/search.ts` by name, folder, branch or commit, and agent, in the order of the Needs you panel and then the Sessions list. Enter presses a session's Jump, or shows its row, through `useShowSession` in `hooks/dom/`, which knows every kind of row: the hero's, the list's and a card of the board. A session the board does not draw, past the cards its column shows, has the line that counts it focused instead. `?` opens `ShortcutsDialog`, which lists `shortcutGroups`.

The Needs you panel, in `components/hero/`, lists the sessions that need you, longest wait first, and the Sessions list leaves them out. Under them the Waited on you bars draw how long each session waited, which `lib/sessions/waits.ts` works out with `lib/charts/timeline.ts` over the time the page holds, and the panel ends with the counts of sessions working, idle and stale, and of every session. The Last hour chart, built in `lib/charts/lastHour.ts`, takes the mean of the history's counts over each five minutes of the clock. Once there is more than one agent to name, each row of the Sessions list names its agent in plain text in an Agent column: the session's own `agent` when it has one, otherwise its source's `label`. The agents counted are the tools that are there and the agents the sessions name, so a folder of status files counts only through the agents in it. When the card is too narrow for every column, the App column gives way first, then the Folder column. A working session whose `lastWriteAt` is 5 minutes or more behind the clock says how long under its status and time, `quiet for 12m`, with the time of the write in a tooltip. `quietFor` in `lib/sessions/quiet.ts` is the rule: working sessions only, from that threshold on, and nothing for a session with no `lastWriteAt`. It changes no status and no group, so it never puts a session in the Needs you panel. A session's branch, or its commit, is drawn by `components/sessions/Branch.tsx`, under the folder's name in the Sessions list and after it in the Needs you panel. `Jump` in `components/jump/Jump.tsx` draws every Jump, in the panel and in the list: a link for a session with a `links.open` that `safeJumpLink` allows, and a button for a session with a `jump`. A press of the button goes through `requestJump` in `lib/api/jump.ts`, which sends `POST /api/jump` through `apiRequest`, and `hooks/data/useJump.ts` keeps what it came to for four seconds, which `JumpNote` shows as a badge by the session's name and says in a status line for a screen reader. The hook sends no press within a second of the last answer, since the route would refuse it. A press of a terminal tab's Jump waits up to 65 seconds, a little longer than the collector waits for osascript. The first such press for each app on a browser also sets `asking` once it has waited a second, since a press macOS does not hold is answered sooner, and `JumpNote` then says on a line under the name that macOS will ask once; `lib/api/automationNote.ts` keeps the apps it has said this for in local storage under `agent-lookout-automation-note`, or in memory while storage is blocked. When the answer is `not-allowed`, the line says where to allow it, and the outcome stays for twelve seconds. A switch in the Sessions card's head groups the same rows by repository, or shows the sessions as a board. `repositoryGroups` in `lib/sessions/repositories.ts` takes the rows in the list's own order and puts them in a group for each `git.repository.id`, in order of name and then of id, with the sessions in no repository last, so each group keeps the order of the status groups; the sessions that need you are the hero's here too. For the board, `boardOf` in `lib/sessions/board.ts` lays the sessions in four columns, Needs you, Working, Idle, and Finished or failed, in the list's own groups and order, and hands back any session whose status is unknown, which has no column, and `repositoryBeside` names the repository before the folder on a card whose folder is named otherwise. `lib/shell/sessionsLayout.ts` keeps the choice, `list`, `repositories` or `board`, in local storage under `agent-lookout-sessions-layout`, or in memory while storage is blocked. A card moves column only because the next snapshot says its session's status changed; nothing on the board writes anything back. The Events log, built in `lib/events/events.ts`, adds a row wherever the history shows a break in the polls. When the page comes back into sight, the log draws a line under the events that arrived while it was hidden and counts them in its head. `nextNewSince` in `lib/events/newSince.ts` is the rule, worked out from one time, when the log was last on screen, and `hooks/data/useNewSince.ts` feeds it from `App`, which outlasts the Overview, and keeps that time in local storage under `agent-lookout-last-looked`. The Timeline, built in `lib/charts/timeline.ts`, draws each session's status over the last hour from the snapshot, the events and the history, and hatches each row where that session's status is not known. The Timeline, the Last hour chart and the Waited on you bars all take the time that was measured from `lib/charts/measured.ts`, so they agree on it.

`src/dashboard/lib/api/collectorStore.ts` polls `/api/sessions`, `/api/events` and `/api/history` every two seconds and never starts a poll while the last one is still running. It holds the last hour of history: it asks for the whole hour at first, then for the last 15 minutes on each beat, which it joins to what it holds. If the collector stops answering for more than five seconds, the last good data stays on screen under a notice that says when it was read. Durations tick every second from the clock in `src/dashboard/hooks/data/useNow.ts`, using the timestamps already loaded, without another request.

The store polls on a beat it is handed, and `lib/api/beat.ts` has two. `timerBeat` is the page's own timer and the default. `workerBeat`, which the app gives its own store, is a worker, `lib/api/beatWorker.ts`, that keeps time and does nothing else. A browser can slow the timers of a page in a background tab to as little as one a minute, and a worker's timer is not slowed that way in Chrome, where this was measured. So the page goes on polling its own server every two seconds while its tab is hidden, and learns that a session is waiting without that delay. If the worker cannot be made, fails, or is not heard from within ten seconds, the beat falls back to the page's timer. The worker is loaded from the app's own address, which the standalone server's `script-src 'self'` allows.

A session that starts waiting, finishes, fails or ends can send a notification. These are the four events, `NoticeEvent` in `src/core/notices/sessionChanges.ts`: `needs-you`, `finished`, `failed` and `ended`. `waitChanges` in the same file decides which sessions began to wait: it compares each snapshot with what it remembered from the one before, and returns the sessions that began to need you and the ids of those that stopped. Only a source that could be read is compared, and a source's first such answer is a baseline that announces nothing, as in the poller. A source that is `not-set-up` counts as read, with no sessions, so a wait in a folder of status files made later is announced. A session that still needs you, with a later status time than its wait has been seen with, was answered and asked again between two polls, so it has stopped and started. A new reason on the same wait, with no later status time, announces nothing. When a source gives no status time, two waits less than a poll apart are seen as one.

`sessionChanges`, beside it, runs `waitChanges` and adds the other three, by the same rules and the poller's rule for a source read in more than one way: it remembers every session of each source at its last answer that could be read in each way, by the `basis` in the snapshot, compares only a source that answered, and compares each answer only with the last one read the same way, so the first answer read a way is a baseline. A background job that only the claude command lists is missing while the registry is read alone, and has not ended. A remembered session whose status becomes `finished` or `failed` has finished or failed. A remembered session that is gone from the list has ended, unless it was finished or failed already, since it said what happened when that changed. A session first seen already over announces nothing, so a source that lists a day of finished jobs at once announces none of them. Each change is one event, and an ended session is reported as it was last seen. It also remembers which sessions are known to be over, listed as finished or failed or said to have ended, until one is listed running again or no list of its source holds it, so an end seen while one way was in use is not told again when the other way is next compared with its own, older, answer. The page, the collector's own notifications, email and the webhook all run it.

`lib/notifications/waitNotifier.ts` carries that out through the notification host. For each change whose event is on it shows one notification, with the session's name as the title, the reason in the Needs you panel's words or Finished, Failed or Ended as the body, from `changeNotice` in `src/core/notices/waiting.ts`, and the tag `agent-lookout:<session id>`, one for each session whatever the event, so a later one takes the place of the earlier. It closes the notification of each session whose wait stopped. A notification that a session finished, failed or ended stays until the person clears it, or until that session's next notification, which closes it first: a browser that puts a notification in the place of another with the same tag does it without a sound. When `/api/history` gives a new `startedAt`, the collector has been restarted under an open page, and the notifier begins again from a baseline. `hooks/notifications/useWaitNotifications.ts` runs it from `App.tsx`, on every view. It listens to the store itself, not to a render, so it works while the tab is hidden, and it closes the notifications of waits when notifications or Needs you are turned off, and on `pagehide`.

Two pages open at one address give a wait the same tag, so the browser keeps one notification for both, and only the page that made it can close it. A page that leaves therefore names the sessions whose notifications it closed on a `BroadcastChannel`, in `lib/notifications/notificationHandover.ts`, and a page that stays shows them again for the sessions it still sees waiting.

`lib/notifications/notificationSetting.ts` keeps the choice, `on` or `off`, in local storage under `agent-lookout-notifications`. It is off by default. A notification is sent only while the choice is on and the browser's permission is granted, and both are read at the moment of sending. `turnOnNotifications` is the only code that asks for permission, and the Settings card calls it from a click. The events are kept beside the choice, under `agent-lookout-notification-events`, as names separated by commas, and are `needs-you` alone until the person switches one. `chooseNotificationEvent` switches one and asks the browser nothing. Both keys are followed across tabs at one address through the `storage` event. The Settings card lists the events, each with a `SegmentedControl` of Off and On, only while notifications are on.

`apiRequest` adds the `X-Agent-Lookout-Notifications` header to every request, written from `notificationEventsInForce`: the events chosen while that same setting is on, which is while the page shows notifications itself, and none otherwise. It is read at each request, and added at the seam so that no request goes without it. When what it says changes, as when notifications go on or off or an event is switched, `useWaitNotifications` asks for `/api/health` at once, with `keepalive`, so the collector hears the change without waiting for the next poll, and still hears it when the tab is closed straight after.

The interface is built from the tokens in `src/dashboard/styles/index.css` and the primitives in `src/dashboard/components/ui/`.

## Notifications from the collector

A dashboard page can only notify while it is open. The poller runs for as long as the app does, so the collector shows the notification itself when no page is going to. The code is in `src/collector/notifications/`.

`serverNotifications.ts` is handed each snapshot by the poller and runs `sessionChanges` over it, the same rule the page runs, so the same changes are announced: none for what was already true when the collector started, and one for each change after that. What a notification says comes from `changeNotice` in `src/core/notices/waiting.ts`, which the page's notifier uses too: the session's name as the title and the reason, with what a waiting session is asking after it, or Finished, Failed or Ended, as the text. A wait held back is shown as the session is at the poll it is shown on, so what it is asking can be said when its transcript was read a poll late.

Whether they are on, and for which events, is not stored. The collector keeps the last thing a page said in the header, in memory. Until a page has said anything they are off, unless `AGENT_LOOKOUT_NOTIFICATIONS=on` was in the environment when the collector was built, which turns on `needs-you` alone, and a page that says `off` later still turns them off. So the one setting in the dashboard covers both, and a collector that is started again has to be told again.

Each change is announced once while an open page keeps asking on time. The collector always learns of a change first, because a page learns of it from the collector's answer. So it holds its notification back, one for each event of each session, and `heldWaitOutcome` in `heldWait.ts`, a pure function of the times involved, decides on each poll what becomes of it, for every event alike. The rules below say a wait, and hold for a finish, a failure and an end too:

- If a page that said `on` has fetched `/api/sessions` since the wait was seen, that page has the wait and shows it, and the collector drops its own. A page that has only just loaded is the exception: its first answer is a baseline and announces nothing, so a wait that begins within a poll of a reload is announced by neither.
- If no page that said `on` has asked for anything in the last 5 seconds, there is nobody to wait for, and it is shown at once.
- Otherwise it is held for 3 seconds and then shown. Polls are 2 seconds apart, so that is the second poll after the wait was seen, about 4 seconds on.
- If notifications, or its event, are turned off meanwhile, it is dropped. If the wait ends meanwhile, it is forgotten. A finish, a failure or an end does not stop being true, so it stays held.

`systemNotifier.ts` shows the notification. On macOS it starts `/usr/bin/osascript` through `runOsascript` in `src/collector/processes/osascript.ts`, the runner Jump uses too, with `execFile`, no shell, stdin closed and a 5 second timeout. The title and the text are each made one line by `oneLine` first, the title cut at 80 characters and the text, which holds the reason and what a waiting session is asking, at 240. The script is fixed: an `on run argv` handler that calls `display notification` with two items of `argv`. The title and the text follow a `--` as arguments, so a session's name is never part of the script and is never read as an option of `osascript`, which without the `--` a name beginning with a dash would be. A failure shows nothing and is not reported.

macOS shows such a notification as coming from Script Editor, except in the Mac app, which shows its own: see [The Mac app](#the-mac-app). Nothing in it can open the session, and the collector keeps no handle on it, so it is not taken down when the session moves on. A page that goes more than about 4 seconds without fetching `/api/sessions` can miss the 3 seconds it is given, and one that asks for nothing for more than 5 seconds is taken to be closed. Either way the collector shows the wait and the page shows it too when it next fetches, so a wait can be announced twice when a browser has slowed a hidden tab down that far or the machine has just woken. A finish, a failure or an end is then always announced twice, since it is still news when the page fetches.

## Email from the collector

Email notifications are off unless the environment the collector starts with sets them up. The code is in `src/collector/email/`, on top of the rules in `src/collector/outbound/`, which the webhook follows too.

`readEmailSetup` in `emailSettings.ts` reads `AGENT_LOOKOUT_EMAIL_TO`, `AGENT_LOOKOUT_SMTP_URL`, `AGENT_LOOKOUT_EMAIL_FROM`, `AGENT_LOOKOUT_EMAIL_AFTER` and `AGENT_LOOKOUT_EMAIL_EVENTS` once, when `createCollector` runs. Email is on only when the first two are set and all five can be read. The events are read by `readNoticeEvents`, the reader the dashboard uses for its storage: one or more of the four names, separated by commas, and `needs-you` alone when the setting is left out. Without `AGENT_LOOKOUT_EMAIL_TO` it is off with nothing to say, whatever else is set, because leaving that one out is how it is turned off. The address must be one address with nothing in it that could be read as a second one or a header. The mail server's address must begin `smtps://`, which is TLS from the start, or `smtp://`, which must switch to TLS with STARTTLS unless the server is `127.0.0.1` or `localhost`. Only its user name, password, server and port are read, and an address with a path, a query or a fragment after them cannot be read, since that is most often a password with a character left unescaped. The delay and the events are read by `readAfter` and `readEvents` in `outbound/outboundSettings.ts`, which the webhook's settings use under their own names. Anything that cannot be read turns email off, and `createCollector` prints one line naming the setting through the `warn` it is given, which the standalone host points at its own printer. No sentence it makes holds a value. With email off, `createCollector` makes no sender and nothing for the poller to call, so the mail library is never loaded.

With email on, `createEmailNotifications` in `emailNotifications.ts` is handed each snapshot after the poll. It gives `createOutboundChannel` in `outbound/outboundChannel.ts` what an email is, `waitEmail` and `overEmail`, and how it goes, the sender, and the channel does the rest, for email and the webhook alike, each with its own memory and its own count. The channel runs `sessionChanges` over each snapshot, the rule the dashboard and the collector's own notifications run, so nothing already true when the collector started is ever emailed. Only the events in the settings are emailed. A session that finished, failed or ended is due at once, and is kept, in the order seen, until the hourly limit lets it go. Each wait that begins after that is kept with the time it began: the session's status time, or the moment it was seen when there is none. The status time of each wait that was emailed, or was open at the start, is kept as well, because a session that misses a poll comes back from `waitChanges` as a wait that started: with the same status time it is the same wait, and is not emailed again. A wait not yet emailed that misses a poll keeps the time it began. `sendTiming` in `outbound/outboundTiming.ts`, a pure function of those times, the delay and the times of the emails of the last hour, says on each poll whether a wait is due. A wait is due once it has lasted the delay and the session still needs the person in this snapshot. A source that did not answer leaves its waits held, and a wait that ends is forgotten. At most `SENDS_PER_HOUR`, 20, are tried in any hour by each channel, whatever they are for: a wait that is due past that is held until an hour has passed since the oldest of them, and sent then if it is still open, and a finish, a failure or an end is sent then as well. When the limit lets some go, the finishes, failures and ends held back go first, oldest first, and then the waits still open. Each is tried once, whether or not the email goes. The emails are sent one after another, after the poll has finished, and nothing a sender does can reach the poll.

`waitEmail` in `emailMessage.ts` writes the email for a wait: plain text, with a subject of the session's name and `waitingPhrase` from `src/core/notices/waiting.ts`, the reason in the words the dashboard uses, and a body of how long it has waited and since when, the project folder's name, `surfaceLabel` for the app, which leaves out an app that is not known, the source's label for the agent, and how to stop these emails. `overEmail` writes the one for the other events: a subject of the name and `overPhrase`, such as `billing-webhooks finished`, and a body that says when the collector saw it, then the same facts. Every value from a session goes through `oneLine` in `src/core/text.ts`, which turns line breaks, control characters and the marks that reorder text into spaces and cuts it to 80 characters, so nothing in a name can begin another line. The same file holds the one rule every name another program wrote is cleaned by: a session's name from any agent, a branch, a tmux session's name, and the title and text of a notification Agent Lookout shows itself.

`createSmtpSender` in `smtpSender.ts` loads nodemailer with a dynamic `import()` on the first email. It opens a connection for each email and closes it after. `transportOptions` gives the library the server, the port, `secure` for `smtps://`, `requireTLS` for `smtp://` and `ignoreTLS` only for a server on this machine, the user name and password, the name `[127.0.0.1]` to greet the server with in place of this computer's name, 10-second timeouts and no logger. Those timeouts count only silence, so each email also has a deadline of three of them in all, past which it counts as not sent and the next may go. A certificate is always checked. A subject with `=?` in it is sent as encoded words, so a mail program shows it as written. A failure becomes a short reason chosen from the error's code alone, because the library's message can repeat what the server said.

`GET /api/email` answers from `status()`: whether email is on, the address with all but its first letter before the @ hidden, the events, the delay, the problem while it is off, the last email's outcome, and, while the hourly limit is full, when the next may go. The server, the user name and the password are never in it. The dashboard reads it through `fetchEmailStatus` in `lib/notifications/emailStatus.ts`, which goes through `apiRequest`, from `hooks/notifications/useOutboundStatus.ts` while Settings is showing, every 5 seconds. `emailWords` turns it into the Email card's two lines, and the This copy card says that the emails leave the computer while email is on.

## Webhook from the collector

Webhook notifications are off unless the environment the collector starts with sets an address for them. The code is in `src/collector/webhook/`, and what is posted and when is decided by the same `createOutboundChannel` that decides it for email, so the two cannot drift apart.

`readWebhookSetup` in `webhookSettings.ts` reads `AGENT_LOOKOUT_WEBHOOK_URL`, `AGENT_LOOKOUT_WEBHOOK_EVENTS` and `AGENT_LOOKOUT_WEBHOOK_AFTER` once, when `createCollector` runs. Without the address it is off with nothing to say, whatever else is set. The address must parse as a URL, begin `https://`, or `http://` only to `127.0.0.1` or `localhost`, name a host that `isWebhookHost` in `src/core/api.ts` takes, hold no user name or password, and be 2,048 characters or fewer. `isWebhookHost` takes a name of letters, digits, dashes and underscores between dots, perhaps with a dot at the end, or an address in brackets, of at most 253 characters, and the dashboard reads the host by the same rule. The events and the delay are read by the shared readers. Anything that cannot be read turns the webhook off, and `createCollector` prints one line naming the setting through `warn`. The address is a secret, since whoever has a Slack incoming webhook's address can post to its channel, so no sentence holds any part of it. With the webhook off, `createCollector` makes no sender and nothing for the poller to call.

`waitPost` and `overPost` in `webhookMessage.ts` write the post: `text`, one line for a person, from `sessionTitle`, `waitingPhrase` or `overPhrase` and `formatDuration`, followed in brackets by the folder's name, `surfaceLabel` for the app and the agent, each left out when it is not known; then `event`, `reason` for a wait, `session` with the same four facts, `at` in ISO 8601, and `waitedSeconds` for a wait. Every value from a session goes through `oneLine`. `slackSafe` then writes `<`, `>` and `&` in `text` as entities and follows each `@` with a space of no width, so a name cannot make Slack mention someone, ping a channel or show a link under other words, nor ping a channel on a service that reads plain mentions. Slack shows the line as it is, so an incoming webhook needs nothing more, and Discord takes it at its address with `/slack` added.

`createHttpSender` in `webhookSender.ts` sends each post with Node's own `https.request`, or `http.request` for an address on this machine, loaded with a dynamic `import()` on the first post, on a connection of its own, `agent: false`, that is closed after the answer. It passes `rejectUnauthorized: true`, so the certificate is checked even when `NODE_TLS_REJECT_UNAUTHORIZED=0` is in the environment. The headers are `Content-Type: application/json`, `Content-Length` and `User-Agent: Agent Lookout/<version>`, and Node adds `Host` and `Connection: close`. Node follows no redirect and keeps no cookie, and nothing is retried. A 2xx is sent, a 3xx is a redirect that is not followed, and any other status, or an error, becomes a short reason chosen from the status or the error's code alone, never from the message, which can hold the address. A post that has no status within 10 seconds counts as not sent and its connection is closed.

`GET /api/webhook` answers from `status()`: whether the webhook is on, `url.hostname` alone, the events, the delay, the problem while it is off, the last post's outcome, and, while the hourly limit is full, when the next may go. The dashboard reads it through `fetchWebhookStatus` in `lib/notifications/webhookStatus.ts`, from the same `useOutboundStatus` hook, and `readWebhookStatus` counts it as on only with a host that `isWebhookHost` takes, the rule the collector took the address by, so the card never says off while posts go out. `webhookWords` turns it into the Webhook card's two lines, beside the Email card, with the words both cards share from `lib/notifications/sendingWords.ts`, and the This copy card says that webhook posts leave the computer while it is on.

## The command

`bin/agent-lookout.mjs` is the `agent-lookout` command, which `package.json` names under `bin` and `npm run status` runs. In a clone it registers tsx and loads `src/cli/agentLookout.ts`, so the command is TypeScript run without a build, as the server is. Installed from npm, where there is no `src/`, it loads `dist/cli/agent-lookout.js`, which `scripts/build-package.mjs` bundles from the same file with esbuild, each dynamic import in a file of its own and the MCP SDK, zod and nodemailer left to `node_modules`. Either way it says what the dashboard says in the same words: the reasons come from `waitingLabel` in `src/core/notices/waiting.ts`, and the length of a wait from `formatDuration` in `src/core/duration.ts`, which the page uses too. Loading tsx is most of the tenth of a second a run takes in a clone. If loading fails, or anything else goes wrong that the command does not expect, the file prints one line and exits with 2, and an output whose reader has gone away is ignored, so the exit code still says what was found. `arguments.ts` reads the command line.

`agent-lookout status` makes one request, `GET /api/sessions`, and makes it only to this machine. `localServer.ts` takes the address from `--url`, or else from `AGENT_LOOKOUT_URL`, or else tries `http://127.0.0.1:4777` and then `http://localhost:5173`, giving each half a second. It accepts only `http` at `localhost`, `127.0.0.1` or `[::1]`, refuses any other address before connecting, and hands the connection the loopback addresses itself, so `localhost` is never looked up. The request has no `Origin` and no `X-Agent-Lookout-Notifications` header, so the handler's checks let it through as they let `curl` through, and what the collector believes about the dashboard's pages is left as it was. The answer is checked for the fields the command reads before anything is printed.

`statusReport.ts` counts the sessions as the Overview counts them, keeps the waits in the order the collector sends them, which is the Needs you panel's, and writes the three outputs: lines for a person, the bare count and JSON. A name is cleaned before it is printed as text. Escape sequences are taken out, every other control character and the marks that reorder text become spaces, and it is cut at 40 columns, counting East Asian wide letters and emoji as two, so the columns line up. In JSON the name is kept exactly, with those characters written as `\u` escapes. tmux reads a `#` in a status-line command's output as its own formatting and shows `##` as one `#`, so when `runByTmux` finds `TMUX` set with neither stdin nor stdout a terminal, which is how tmux runs such a command, each `#` in a name is doubled. The exit code is 0 when nothing needs you, 1 when a session does and 2 when the answer is not known: the server did not answer, its answer could not be read, the command line was wrong or the command could not run, each said in one line on stderr, or no agent has been read yet, which the output says in place of the counts.

`agent-lookout mcp` is a Model Context Protocol server over stdio, in `src/cli/mcp/`. The agent's app starts it, so it listens on no port. `agentLookout.ts` takes its address as `status` does and refuses one that is not loopback before it starts, then loads `mcpServer.ts` with a dynamic `import()`, so `status` never loads the protocol's library. `mcpServer.ts` builds the server with the official SDK, `@modelcontextprotocol/sdk`, and `zod` for the one input schema, registers three tools, each marked read-only, and speaks over the streams it is given until stdin ends, then closes and exits with 0. Each call runs `findSnapshot` in `localServer.ts`, which `status` runs too: one `GET /api/sessions` to each address in turn, so a call says exactly what `status` would when Agent Lookout cannot be reached, as an error answer, and the server goes on serving. `toolAnswers.ts` is pure: from one snapshot and the clock, `listSessions`, `sessionsNeedingYou` and `sourceList` give each tool's answer as JSON, sent both as text and as structured content. They order the sessions with `sortSessions` from the core, count them with `statusReport`, and give a source's state in the Sources view's words, `SOURCE_STATE_LABEL` in the core. Every field beyond what `asSnapshot` checked is checked before it is used, and one of the wrong kind is taken as not known. Every text from a session or a source has the characters that show nothing taken out, Unicode's format characters such as zero-width spaces and tag characters and the variation selectors, and then goes through `terminalText`, cut at 200 columns for a session's and 1,000 for a source's sentences. Each tool's description, the server's instructions and every answer say that this text is data, and the summary of the waits writes each name as a JSON string, in quotation marks, and names any source in error, so a count made without it is not read as nothing waiting.

## On Linux

The collector is plain Node and the dashboard a web page, so both run on Linux as they are. Three things look at the system, each in one place, and do something on macOS alone: `createSystemNotifier` shows notifications, `createOsascriptRunner` runs `osascript` for Jump, and `readProcessTableWithPs` asks `ps` for each process's terminal and program, which only Terminal and iTerm2 need. On any other system the first shows nothing, and `createCollector` then prints one line at start when `AGENT_LOOKOUT_NOTIFICATIONS=on` asks for them. The others run nothing. Everything else runs the same on both, `ps` included: `parseProcessStarts`, `parseProcessParents` and `parseProcessTable` read what the `ps` of macOS prints and what procps, the `ps` of Linux, prints, and their unit tests give them both. Windows is not supported: `ps` and tmux are never run there.

## Tests

`vite.config.ts` defines three Vitest projects and picks a test's project by its folder. `tests/unit/` and `tests/integration/` run in Node. `tests/component/` runs in headless Chromium, because those tests assert computed styles and layout. A test sits at the path of the module it covers, with `tests/<group>/` in place of `src/`.

The config leaves the collector plugin out of test runs, so a test never starts the poller or reads real sessions from the machine it runs on. The Mac app's main process is tested without Electron: the request adapter, the scheme's handler, the link and permission rules and the window's state and frame are modules that import nothing from it.

CI runs every job on Ubuntu. The `build` job also bundles the Mac app's main process, which stops if the bundle would need a package at run time. Packing the app needs a Mac, so it is not done in CI: `.github/workflows/release-mac.yml` packs it on macOS when a version tag is pushed, and attaches the disk images, the zips and `latest-mac.yml` to that tag's release. The `start` job also builds the app and runs `scripts/start-check.mjs`, as `npm run start:check` does on any machine with a build. It makes folders of its own: a Claude Code registry with one file naming a `sleep` it starts, with that process's real start time, and one naming another `sleep` with a start time that process did not have, a copy of `tests/fixtures/codex-home` and one status file. It starts the app with `npm start` on a port the system picks, with the `claude` command, tmux and Terminal turned off, waits for `/api/health`, and reads `/api/sessions` until each source has been read. It checks that all three sources are `ok`, that the first registry session needs you and the second is left out, that the Codex sessions a lock marks open have the statuses the fixture gives them, and that the status file's session is working. Then it sends SIGINT to npm and each process under it, as Ctrl+C does, checks that the app stopped, and stops the two `sleep`s, each process by its own ID. The `package` job runs `npm pack`, checks that the tarball holds only `bin/`, `dist/`, `package.json` and the listed documents, installs it into a folder of its own and runs the same check there, with `--command npx --yes=false agent-lookout` in place of `npm start`.

[tests/README.md](../tests/README.md) says what belongs in each folder and how to run each group.
