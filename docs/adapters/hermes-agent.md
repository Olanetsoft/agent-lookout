# Hermes Agent adapter notes

These notes record what Agent Lookout reads from Hermes Agent, where each value comes from, and what breaks when Hermes Agent changes. Start here when the adapter stops working.

The adapter was built from Hermes Agent's source at v0.23.3, published 2026-11-19 (commit `caafe53` of [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent)), and from its docs under `website/docs/` at that tag. It has not yet been checked on a computer running Hermes Agent. Hermes Agent was not installed or run where it was written, and nothing in Hermes Agent's own folders there was read. Everything below comes from the source and from databases written by hand with the same tables, so a status can be wrong. [Not yet checked](#not-yet-checked) lists what only a real install can answer. Paths in parentheses are Hermes Agent's files at that tag. At v0.23.3 Hermes Agent moved the code of its session store out of the `hermes_state*.py` files into `persistence/`, and the files it writes, and the tables and columns the adapter reads, stayed as they were.

The code is in `src/collector/adapters/hermes-agent/`, and the status mapping is in `src/core/mapping/hermes-agent/hermesAgentMapping.ts`. The adapter starts the system's `sqlite3` with the helpers the OpenCode and Antigravity adapters use, in `src/collector/adapters/antigravity/app/summaries.ts`.

## How it reads Hermes Agent, and why

The adapter needs nothing installed and changes nothing, but for the one empty `-wal` [below](#how-sqlite3-opens-the-database): no plugin, no setting, no Hermes Agent program run, no network. It looks at each profile's database and the two files SQLite keeps beside it, reads the database's first 20 bytes when it changed, asks the system's `sqlite3` two fixed questions when the database or its `-wal` changed, and while a turn runs, checks the turn's process with signal 0.

Hermes Agent offers other ways in, and none of them can be used that way:

| Interface                                                   | Why it is not used                                                                                                                                   |
| ----------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- |
| Any `hermes` command                                        | It runs Hermes Agent's own code, and a client can start the profile's gateway when none runs (`hermes_cli/gateway_client.py:330-362`)                |
| The gateway's WebSocket API (`/api/ws`)                     | It needs a ticket, and asking it is a request to Hermes Agent                                                                                        |
| `sessions/sessions.json` and `runtime/active_sessions.json` | Their gateway entries hold chat and user ids (`gateway/run_busy.py:371-378`, `gateway/config.py:614-630`)                                            |
| A plugin or an approval hook                                | It needs a change to Hermes Agent's config (`tools/approval_context.py:54-73`). Agent Lookout installs only its own Claude Code plugin               |
| `sessions/<id>.jsonl`                                       | Written only as a fallback, when `state.db` was replaced under a running Hermes Agent (`session_rescue.py:10-23`), and it holds a session's messages |

## Where it looks

- **The root.** `AGENT_LOOKOUT_HERMES_HOME` if set, and then Hermes Agent's own variable is not read. Otherwise Hermes Agent's own `HERMES_HOME`, by Hermes Agent's rule, when it is an absolute path once a leading `~` is the home folder: a folder in `~/.hermes`, or `~/.hermes` itself, has `~/.hermes` as its root; `<x>/profiles/<name>` has `<x>`; any other folder is its own root (`hermes_constants.py:112-119`, `315-327`). Otherwise `~/.hermes`. Hermes Agent follows links in `HERMES_HOME` to tell where it is; Agent Lookout does not, and other `$` variables in it are not filled in.
- **The profiles.** The default profile's database is `<root>/state.db`. A named profile's is `<root>/profiles/<name>/state.db` (`hermes_cli/profiles.py:291-301`, `441-453`; `persistence/sqlite/conversation/_store/sessions.py:325-340`). A name is taken when it matches `[a-z0-9][a-z0-9_-]{0,63}`, as Hermes Agent allows (`persistence/sqlite/conversation/_store/sessions.py:336`; `hermes_constants.py:414`), and is not `default`, and when `lstat` says the entry is a folder, so a link is skipped. Deleted profiles leave a tombstone in `profiles/.deleted`, which the pattern never matches (`hermes_constants.py:331`). The first 16 names in order are read, and `profiles/` is listed at most once a minute. `active_profile`, which names the profile Hermes Agent starts in, is not read: every profile is.
- **Not read:** a home with `HERMES_DATA_DIR_SUFFIX`, which Hermes Agent's desktop channel builds bake into their own environment (`hermes_constants.py:70-77`; `website/docs/reference/environment-variables.md:895`), and Hermes Agent's Windows home, `%LOCALAPPDATA%\hermes`.

## What it reads

| What                                                   | How                                                                                                        | When                                                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| The root folder                                        | One `stat`. Not done when `AGENT_LOOKOUT_HERMES_HOME` is set                                               | On the first poll, at most once a minute while it is missing, and on every poll while no profile has a database                                                                                                                                                                                                                         |
| `<root>/profiles/`                                     | `readdir` of the names, then `lstat` of each that matches the pattern                                      | At most once a minute                                                                                                                                                                                                                                                                                                                   |
| `state.db`, `state.db-wal`, `state.db-shm` of each one | `lstat`. Each must be an ordinary file. An empty `state.db` is taken as none                               | Every poll                                                                                                                                                                                                                                                                                                                              |
| The first 20 bytes of each `state.db`                  | One read-only `open`, a read and a close, in Agent Lookout's own process, of the file `lstat` saw          | When `state.db` changed since the header was last read                                                                                                                                                                                                                                                                                  |
| Each `state.db`                                        | `sqlite3`, with the probe and the sessions query below                                                     | When the database or its `-wal` changed since the last read, by identity, size or modified time, or the `-wal` came or went. After a read that did not work, on the next change or 10 seconds later. When a poll's 5 seconds for reading run out before it, or cut its read short, on the next poll, with its last read kept until then |
| Each `sqlite3` at the fixed places                     | `<path> -init /dev/null --version`, so the person's own `~/.sqliterc` is not run first                     | Before the first read of any database, and again once the program at that place changes, or when a poll's 5 seconds for reading cut its run short                                                                                                                                                                                       |
| A live turn lease's process                            | Signal 0, which asks the system whether it exists and sends it nothing (`src/collector/processes/pids.ts`) | Every poll, only for leases that have not run out                                                                                                                                                                                                                                                                                       |
| Agent Lookout's own `/proc/self/ns/pid`, on Linux only | `readlink`                                                                                                 | The first time a lease is live, and again only after a read that failed, to compare with the lease's `pidns=`                                                                                                                                                                                                                           |

Hermes Agent reads the same 20 bytes itself: its `hermes sessions` journal-mode command opens the file plainly and reads bytes 18 and 19, which are 1 and 1 in rollback-journal mode and 2 and 2 in WAL mode (`persistence/sqlite/admin/_doctor.py:44-46`, `:77-83`; also `hermes_cli/doctor_platform.py:79-92`). Hermes Agent allows such a plain read only in a process that holds no SQLite connection, because closing any file a process has open lets go of that process's own locks on it (`hermes_cli/sqlite_safe_read.py:1-6`). Agent Lookout's process never holds a SQLite connection: only the `sqlite3` it starts does. So its open and close cannot let go of a lock Hermes Agent holds.

The adapter's own code opens nothing else of Hermes Agent's. Only `sqlite3` opens the databases, their `-wal` and `-shm`, and a `state.db-journal` that a write left unfinished, and only as the next section says. Nothing is read on Windows.

A look at one of a profile's three files that fails for any reason but that nothing is there, as when Agent Lookout is refused or a disk fails, is not taken for a missing database, and at the `-wal` or `-shm` it is not taken for no file. That profile is not read, like one `sqlite3` could not read, and the other profiles are read as ever. Its sessions are not listed, and the card names it, or is an error when no other profile is read. The poll leaves it out of `health.parts`, so the poller keeps its last answer and sends no ended for its sessions, and names it in `health.notRead`, so after Agent Lookout restarts its sessions are compared with the history only at the first poll that reads it. The next poll looks again, and the first look that works reads the database.

## How sqlite3 opens the database

`sqlite3` is found and started as for OpenCode and Antigravity: never on `PATH`, directly with no shell, with stdin closed, only `PATH=/usr/bin:/bin` and `LC_ALL=C` in its environment, and at most 4 MiB of output. No run starts once 5 seconds of a poll have passed. The poll's first run gets a timeout of 5 seconds, and each later run 5 seconds or what is left of the poll's 5, whichever is less. A run that does not answer in a whole 5 seconds did not work, and neither did a read whose probe had a whole 5 seconds and whose query did not fit in what was left, since every poll would cut it short the same way. Any other profile whose read those 5 seconds cut short, or did not reach, keeps its last read until the next poll, which starts with it, and one with no last read is left out. When that leaves a poll with no profile read and none failed, the card says Searching: Hermes Agent's databases are still being read. The fixed places are tried in this order: `/usr/bin/sqlite3`, `/bin/sqlite3`, `/opt/homebrew/bin/sqlite3`, `/usr/local/bin/sqlite3`, `/opt/local/bin/sqlite3`, and for Hermes Agent alone, `/opt/homebrew/opt/sqlite/bin/sqlite3` and `/usr/local/opt/sqlite/bin/sqlite3`, where Homebrew keeps its own `sqlite3` without linking it, since macOS has one. Its arguments are `-init /dev/null -batch -json`, in rollback-journal mode `-cmd ".timeout 1000"`, then `-cmd 'PRAGMA trusted_schema=OFF'`, the database's address and one fixed question.

`-cmd 'PRAGMA trusted_schema=OFF'` keeps a view in the database from calling `edit()`, which the `sqlite3` program adds and which starts a program. `sqlite3` turns that setting off itself from 3.42 on, and one older than 3.33 has no `-json`, so this matters for 3.33 to 3.41. Every agent's read has it. The one run without it is `--version`, below, which names no database.

Hermes Agent does not always keep its database in WAL mode. It never switches one to WAL mode while its own Python's SQLite has the WAL-reset bug below, and keeps such a database in rollback-journal (`DELETE`) mode; it never switches one back once it is in WAL mode (`sqlite_support.py:345-437`, `556-592`). `DELETE` mode is also set by `database.journal_mode: delete` (`sqlite_support.py:165-175`), on virtiofs and 9p mounts such as Docker's and OrbStack's (`:212`, `:423-431`), and on a disk that refuses WAL mode (`:33-37`). A new database on NFS, SMB or sshfs is left in rollback-journal mode unless `database.journal_mode` is set (`:227`, `:432-436`). So the address follows the header's bytes and the files beside the database:

| State of `state.db` and the files beside it                  | Address                                                        | Why                                                                                                                                                         |
| ------------------------------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Header 1/1 (rollback journal), no `-wal`                     | `file:<database>?mode=ro&readonly_shm=1`, with `.timeout 1000` | Hermes Agent writes pages straight into `state.db`, so `immutable=1` could read a commit half-written. A shared lock waits a commit out, for up to a second |
| Header 2/2 (WAL), no `-wal` or an empty one                  | `file:<database>?mode=ro&immutable=1`                          | Nothing is in a `-wal`, so the file is whole. `immutable=1` takes no lock and makes no file                                                                 |
| Header 2/2, a `-wal` that holds something, and `-shm`        | `file:<database>?mode=ro&readonly_shm=1`                       | It reads Hermes Agent's newest commits and opens the `-shm` read-only, so nothing is written to either. Only with a `sqlite3` that passes the test below    |
| Header 2/2, a `-wal` that holds something, no `-shm`         | Not read                                                       | Reading it would make a `-shm`. The card says so                                                                                                            |
| Either sidecar not an ordinary file                          | Not read                                                       | The card says so                                                                                                                                            |
| A `-wal` beside a header of 1/1, or a header that is neither | Not read                                                       | SQLite opens a database in WAL mode whenever a `-wal` is beside it, whatever its header says. The card says `sqlite3` could not read it                     |

`readonly_shm=1` changes nothing for a rollback-journal database, which has no `-shm`. It is there in case Hermes Agent switches the database to WAL mode between the read of its header and the open: a reader without it would open the `-shm` to read and write and write a mark in it.

Every read is made with a `sqlite3` that passes the WAL-reset test below when one is found, whatever the header says, so a database switched in that moment is still read safely. With only ones that fail it, a rollback-journal database, or a WAL database with no `-wal` to read, is read with the first found, and after the read the `-wal` is looked at again with `lstat`, and the header read again when `state.db` changed. If the database went to WAL mode as it was read, or a `-wal` came beside it, or, in WAL mode, the `-wal` came to hold something, what was read is dropped (`switched` in `database.ts`): the profile keeps its last read and its sessions, and the next poll reads it first, by what the files then are. A look that fails then counts as one of these. The open itself cannot be held off, so in that moment a `sqlite3` that fails the test can still open a live WAL database: one that was in rollback-journal mode as it was looked at with `readonly_shm=1`, which keeps it from writing to the `-wal` or the `-shm`, and one already in WAL mode with no `-wal` to read with `immutable=1`, which reads the database file alone. Hermes Agent switches a database to WAL mode once, when its own SQLite passes the test, and never back.

`-cmd ".timeout 1000"` is new beside OpenCode's arguments. A WAL reader does not wait on writers, but a rollback-journal reader does: Hermes Agent raised its own read wait to 5 seconds after "database is locked" failures (`persistence/sqlite/_holder.py:87-91`). Its writers wait up to 20 seconds, transcript writes up to 60, and activity writes half a second before they skip (`persistence/sqlite/_holder.py:243`). So a read of a few milliseconds costs at most one skipped activity write, which Hermes Agent makes again in its next minute. A read that ends in "disk I/O error" or "database is locked" does not work, and is tried again 10 seconds later. Hermes Agent itself retries the first for its own read-only opens while a checkpoint runs (`persistence/sqlite/_holder.py:79-86`).

Opened without `immutable=1`, `sqlite3` also looks for a `state.db-journal` beside the database, as any SQLite program does (`hasHotJournal` in `src/pager.c`). In rollback-journal mode Hermes Agent writes one for each write and deletes it when the write ends, so one stays only when a write did not finish, such as when Hermes Agent was killed in the middle of it. When no write holds the database, `sqlite3` opens that journal read-only to see whether it holds a write to undo. With `mode=ro` it never undoes it or writes to it: when the journal holds a write to undo, `sqlite3` stops with "attempt to write a readonly database", and the profile is not read until Hermes Agent opens the database again and undoes the write itself.

### The WAL-reset test

A database in WAL mode whose `-wal` holds something is read only with a `sqlite3` that passes Hermes Agent's own test for SQLite's WAL-reset bug, copied exactly (`is_sqlite_wal_reset_vulnerable` in `hermes_cli/sqlite_runtime.py:23-30`; the same rule at `sqlite_support.py:801-808`). It counts SQLite from 3.7.0 up to, not including, 3.51.3 as having the bug, except 3.44.6 and the later 3.44 releases, and 3.50.7 and the later 3.50 releases.

Hermes Agent refuses a `sqlite3` with the bug even to salvage a copy of a database: such a program opening a live database can delete its `-wal` and `-shm` and split it in two, losing writes Hermes Agent had already confirmed. It adds that Debian's and Ubuntu's `sqlite3` are often in that range, 3.45.1 for one (`persistence/sqlite/admin/_lost_and_found.py:74-95`). Its source does not say whether a `mode=ro&readonly_shm=1` reader can cause the split, so the adapter follows Hermes Agent.

So before the first read of any database, each fixed place is asked `-init /dev/null --version`, once, and again only when the program there changes by identity, size or modified time, or a poll's 5 seconds for reading cut that run short, and the first that passes is used for every database. One whose answer cannot be read fails the test. When none passes, a profile with a live `-wal` is not read, and the card names the first `sqlite3` found and its version, and says to install 3.51.3 or newer: on a Mac with `brew install sqlite`, which the two Homebrew places above find, and elsewhere at `/usr/local/bin/sqlite3`, such as sqlite.org's precompiled tools. macOS's own `/usr/bin/sqlite3`, 3.51.0 at the time of writing, fails the test. A rollback-journal database, or a WAL database with no `-wal` to read, is then read with the first `sqlite3` found, as above: the bug is in WAL mode alone.

### What a read can leave behind

`tests/integration/collector/adapters/hermes-agent/database.test.ts` runs the real `sqlite3` on databases written by hand with Hermes Agent's tables: one in rollback-journal mode, one in WAL mode with no `-wal`, and one whose commits lie only in the `-wal` of a second `sqlite3` that keeps it open, as Hermes Agent would. It checks the rows read, and that no byte, size or modified time of the database, its `-wal` or its `-shm` changes. It also switches a rollback-journal database to WAL mode with a commit in its `-wal` as it is read: with a `sqlite3` taken to pass the test the read stands, and with one taken to fail it the read is dropped, no file changes, and the next read reads none of it. It has not been run against Hermes Agent itself. The same file kills a write in the middle of a rollback-journal database, which leaves a `state.db-journal` with a write to undo, and checks that the read fails, is tried again 10 seconds later, and changes no byte, size or modified time of the database or the journal, and that the database is read as it was before the write once a `sqlite3` that may write opens it.

If a program closes the database between the `lstat` and the read, and SQLite removes the `-wal` and `-shm` as it does then, a `sqlite3` built from SQLite's own source, as on Linux, makes an empty `state.db-wal` in Hermes Agent's folder as it opens the database (`sqlite3WalOpen` in `src/wal.c`), and that read does not work. SQLite has no setting that stops it. The next read opens the database as a file nothing changes. `/usr/bin/sqlite3` on macOS was seen to make none. This is the same case as OpenCode's, and #148 decides it for both.

## The two questions

Both are fixed text. Nothing from a file, a request or a setting is put into them, and every cut-off is worked out inside SQLite. They follow Hermes Agent's own advice to tell its versions apart by their columns, "never by this number" (`persistence/sqlite/_schema_ddl.py:68-72`): `schema_version` is not read.

The probe asks for the names of three tables and of their columns alone:

```sql
SELECT 'table' AS kind, name FROM sqlite_master
  WHERE type = 'table' AND name IN ('sessions', 'messages', 'session_turn_leases')
UNION ALL SELECT 'sessions', name FROM pragma_table_info('sessions')
UNION ALL SELECT 'messages', name FROM pragma_table_info('messages')
UNION ALL SELECT 'session_turn_leases', name FROM pragma_table_info('session_turn_leases')
```

The sessions query is asked only when the probe finds the three tables, with `id`, `source`, `created_source`, `parent_session_id`, `started_at`, `ended_at`, `end_reason`, `cwd`, `title`, `title_source`, `model_config`, `session_key`, `archived`, `hidden`, `last_activity_at` and `last_activity_description` in `sessions`; `id`, `session_id`, `role`, `timestamp`, `active`, `display_kind`, `display_metadata`, `finish_reason`, `tool_calls` and `tool_call_id` in `messages`; and `conversation_id`, `holder`, `acquired_at` and `expires_at` in `session_turn_leases`. `created_source` first ships in Hermes Agent v0.21.6, published 2026-10-08, so that is the oldest version read. An older database makes the card say it is laid out as a version Agent Lookout does not read. `title_source` is older than `created_source`: it first ships in v2026.8.13 (`persistence/sqlite/admin/_schema_history.py:199`, `:208`), and Hermes Agent adds every column a database lacks at once (`_reconcile_columns`, `persistence/sqlite/_schema.py:842-859`). So a database with `created_source` has `title_source`, and needing it turns away no version that `created_source` lets in.

```sql
WITH RECURSIVE
cut(t) AS (SELECT CAST(strftime('%s', 'now') AS REAL) - 172800),
recent(id) AS (
  SELECT s.id FROM sessions s, cut
  WHERE max(s.started_at, coalesce(s.ended_at, 0), coalesce(s.last_activity_at, 0)) >= cut.t
    OR EXISTS (SELECT 1 FROM messages m WHERE m.session_id = s.id AND m.timestamp >= cut.t)
),
up(id, root, depth) AS (
  SELECT id, id, 0 FROM recent
  UNION ALL
  SELECT up.id, p.id, up.depth + 1
  FROM up
  JOIN sessions c ON c.id = up.root
  JOIN sessions p ON p.id = c.parent_session_id
  WHERE up.depth < 64
    AND p.end_reason = 'compression'
    AND (CASE WHEN json_valid(c.model_config) THEN json_extract(c.model_config, '$._branched_from') END) IS NULL
    AND (CASE WHEN json_valid(c.model_config) THEN json_extract(c.model_config, '$._delegate_from') END) IS NULL
    AND (CASE WHEN json_valid(c.model_config) THEN json_extract(c.model_config, '$._reset_from') END) IS NULL
    AND coalesce(c.source, '') != 'tool'
),
heads(id, root, depth) AS (SELECT id, root, max(depth) FROM up GROUP BY id)
SELECT h.root AS root_id, c.id,
  r.source AS root_source, r.created_source AS root_created_source, r.started_at AS root_started_at,
  (CASE WHEN r.title_source IS NULL OR r.title_source IN ('llm', 'user') THEN '' END) || substr(r.title, 1, 1000) AS root_title,
  substr(r.cwd, 1, 4097) AS root_cwd,
  c.started_at, c.ended_at, c.end_reason, c.last_activity_at,
  (SELECT max(m.timestamp) FROM messages m WHERE m.session_id = c.id) AS last_message_at,
  (CASE WHEN c.title_source IS NULL OR c.title_source IN ('llm', 'user') THEN '' END) || substr(c.title, 1, 1000) AS title,
  substr(c.cwd, 1, 4097) AS cwd,
  (c.last_activity_description LIKE 'waiting for user approval%'
    OR c.last_activity_description LIKE 'waiting for plugin approval transport%') AS approval_label,
  (c.last_activity_description LIKE 'waiting for user clarify response%'
    OR c.last_activity_description LIKE 'waiting for a one-time code%') AS question_label,
  n.role AS n_role, n.timestamp AS n_at, n.display_kind AS n_kind, n.finish_reason AS n_finish,
  CASE WHEN json_valid(n.display_metadata) THEN json_type(n.display_metadata, '$.error') IS NOT NULL END AS n_error,
  (SELECT max(m.timestamp) FROM messages m WHERE m.session_id = c.id AND m.active = 0
    AND m.id >= (SELECT x.id FROM messages x WHERE x.session_id = c.id AND x.active = 0
      AND x.display_kind = 'content_refused' AND x.id > coalesce(n.id, 0) ORDER BY x.id DESC LIMIT 1)) AS refused_at,
  a.timestamp AS calls_at,
  (SELECT count(*) FROM json_each(CASE WHEN json_valid(a.tool_calls) THEN a.tool_calls ELSE '[]' END) q
    WHERE json_extract(q.value, '$.function.name') = 'clarify'
    AND NOT EXISTS (SELECT 1 FROM messages x WHERE x.session_id = c.id AND x.role = 'tool' AND x.id > a.id
      AND x.tool_call_id = json_extract(q.value, '$.id'))) AS open_questions,
  (SELECT count(*) FROM json_each(CASE WHEN json_valid(a.tool_calls) THEN a.tool_calls ELSE '[]' END) q
    WHERE NOT EXISTS (SELECT 1 FROM messages x WHERE x.session_id = c.id AND x.role = 'tool' AND x.id > a.id
      AND x.tool_call_id = json_extract(q.value, '$.id'))) AS open_calls,
  l.acquired_at AS lease_at, l.expires_at AS lease_until,
  CASE WHEN l.holder GLOB 'pid=[0-9]*' THEN CAST(substr(l.holder, 5) AS INTEGER) END AS lease_pid,
  CASE WHEN instr(l.holder, ':pidns=') > 0 THEN CAST(substr(l.holder, instr(l.holder, ':pidns=') + 7) AS INTEGER) END AS lease_pidns
FROM heads h
JOIN sessions c ON c.id = h.id
JOIN sessions r ON r.id = h.root
LEFT JOIN messages n ON n.id = (SELECT x.id FROM messages x WHERE x.session_id = c.id AND x.active = 1
  AND x.role NOT IN ('session_meta', 'system') ORDER BY x.id DESC LIMIT 1)
LEFT JOIN messages a ON a.id = (SELECT x.id FROM messages x WHERE x.session_id = c.id AND x.active = 1
  AND x.role = 'assistant' AND x.tool_calls IS NOT NULL ORDER BY x.id DESC LIMIT 1)
LEFT JOIN session_turn_leases l ON l.conversation_id = h.root
WHERE (r.parent_session_id IS NULL
    OR (CASE WHEN json_valid(r.model_config) THEN json_extract(r.model_config, '$._branched_from') END) IS NOT NULL
    OR EXISTS (SELECT 1 FROM sessions p WHERE p.id = r.parent_session_id
      AND p.end_reason = 'branched' AND r.started_at >= p.ended_at)
    OR (CASE WHEN json_valid(r.model_config) THEN json_extract(r.model_config, '$._reset_from') END) IS NOT NULL
    OR EXISTS (SELECT 1 FROM sessions p WHERE p.id = r.parent_session_id
      AND p.end_reason IN ('session_reset', 'session_switch', 'idle', 'daily', 'suspended', 'resume_pending_expired')
      AND r.session_key IS NOT NULL AND r.session_key != '' AND r.session_key = p.session_key))
  AND (CASE WHEN json_valid(r.model_config) THEN json_extract(r.model_config, '$._delegate_from') END) IS NULL
  AND r.archived = 0 AND r.hidden = 0
  AND coalesce(r.source, '') NOT IN ('kanban', 'tool', 'oneshot')
ORDER BY max(c.started_at, coalesce(c.ended_at, 0), coalesce(c.last_activity_at, 0)) DESC, c.id DESC
LIMIT 500
```

The tables and columns are those of `SCHEMA_SQL` (`persistence/sqlite/_schema_ddl.py:116-451`: `sessions` at 126-195, `messages` at 197-228, `session_turn_leases` at 377-382). Every time is a count of seconds, with a fraction (`persistence/sqlite/conversation/_store/sql_common.py:161-184`), and is kept in milliseconds.

| Field                                                      | Holds, and where it comes from                                                                                                                                                                                                                                                                                                         |
| ---------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `root_id`, `id`                                            | The conversation's root, and the row's own id. ## Which sessions are listed

- **One row per conversation.** The rows of a compression chain share a root and are one session. Its id is the root's, its start is the root's, and its title, folder and status come from the tip: the row that did not end with `compression`, an open one before an ended one, then the one written most recently, in the order of `_CHAIN_STEP_SQL` (`persistence/sqlite/conversation/_store/compression.py:38-46`). When every row ended with `compression`, the one written most recently is the tip.
- **Roots, as Hermes Agent lists them.** A row with no parent, a branch, or a reset child (`_LISTABLE_CHILD_SQL`, `_BRANCH_CHILD_SQL`, `_RESET_CHILD_SQL` and `_RESET_END_REASONS`, `persistence/sqlite/_schema_ddl.py:35-59`; `persistence/sqlite/conversation/_store/sql_common.py:149-150`). Hermes Agent treats a branch or a reset child as a conversation of its own (`persistence/sqlite/conversation/_store/sessions.py:114-131`). Scheduled runs and chats from messaging apps are listed.
- **Not listed:** a subagent's run, with a `_delegate_from` marker; an archived or hidden row (`persistence/sqlite/conversation/_store/sessions.py:114-149`, `1293-1294`); and the sources Hermes Agent hides from people, `kanban`, `tool` and `oneshot` (`INTERNAL_LISTING_SOURCES`, `persistence/conversation/sessions.py:131`, as `hermes_cli/console_engine.py:603-606` uses it). `hermes sessions list` hides only `tool` (`hermes_cli/sessions_cmd.py:331-333`).
- **The window.** A row whose own times or messages fall in the last 48 hours, by SQLite's clock, up to the newest 500 rows. Then each session for 24 hours after the newest time of its rows. A time ahead of the clock counts as it is, so a clock set back hides no session.
- **Not folded as Hermes Agent folds them.** Hermes Agent folds a local session's earlier reset segments into one, using receipts in `state_meta` (`persistence/sqlite/conversation/_store/local.py:87-107`, `147-155`). The adapter does not read `state_meta`, so an earlier segment shows as a finished session of its own.

A session's id in Agent Lookout is `hermes-agent:<profile>/<root id>`, where the profile is `default` or the profile's name. `default` can never be a named profile's name (`hermes_cli/profiles.py:441-445`), and the `/` keeps a second colon out of the id.

## Working, needs you and the turn lease

- **The lease brackets a turn.** Hermes Agent takes it before a turn starts and lets it go in the turn's `finally` (`agent/turn_facade.py:84`, `201-205`; `persistence/sqlite/authority/coordination.py:257-276`, `295-305`). It runs out 300 seconds after it was last written and is renewed every 60 (`agent/turn_facade_lease.py:27`, `55`); a renewal moves only `expires_at` (`persistence/sqlite/authority/coordination.py:278-293`). Hermes Agent itself takes a live lease for a running turn (`persistence/sqlite/authority/_local_migration.py:33-35`). A turn whose agent has no database takes none (`agent/turn_facade_lease.py:327-328`).
- **Live.** A lease is live while `expires_at` is after Agent Lookout's clock, which is Hermes Agent's on the same machine, and its process was not found gone. This is judged on every poll from the rows already read, so a lease that runs out with no file changed ends Working.
- **The process.** At v0.23.3 `hermes chat` runs its turns in the profile's gateway: the CLI process builds no agent and writes no `state.db` (`hermes_cli/gateway_agent.py:1-6`; `hermes_cli/main.py:1491-1498`). TUI, desktop and ACP sessions go through the same gateway (`website/docs/developer-guide/gateway-local-sessions.md:103-117`). So a lease's `pid=` is mostly the gateway's. Each live lease's pid is checked with signal 0, by Hermes Agent's own strict rule for leases (`holder_pid_checkable`, `process_identity.py:110-131`): where there are no pid namespaces, as on macOS, which writes no `pidns` (`:66-68`), the pid is checked; on Linux, only when the holder names Agent Lookout's own pid namespace. A holder that names another, such as Hermes Agent in a container sharing the folder, or none, is not checked, and its lease's expiry is trusted, as it is while Agent Lookout's own namespace cannot be read. A dead pid means the lease is not live, so a gateway killed mid-turn shows as idle at once rather than working for up to 300 seconds.
- **A question.** A `clarify` call with no result while the lease is live is a question that waits, on any surface, when the call is the running turn's: written no earlier than the lease's `acquired_at`. The call's row is saved before the tool runs, and its result after the tool ends. A call an earlier turn left with no result is no wait: Hermes Agent keeps such a call in the database when its gateway is killed while it asks, and deals with it only in what it sends the model next (`strip_dangling_tool_call_tail`, `agent/replay_cleanup.py:120-144`).
- **An approval.** Pending approvals and questions are kept only in Hermes Agent's memory (`tools/approval.py:123`; `tools/clarify_gateway.py:34-36`). The only trace is the activity label. The gateway's wait touches it every 10 seconds as `waiting for user approval (Ns elapsed)` (`tools/approval_gateway_wait.py:87-101`; `tools/approval_human_wait.py:85-95`), and a plugin's approval transport as `waiting for plugin approval transport (Ns elapsed)` (`tools/approval_prompt.py:244-250`; `tools/approval.py:1072-1085`). Hermes Agent saves it at most once a minute (`agent/session_activity.py:21`; `agent/activity_tracking.py:91-130`). So it shows 10 to 70 seconds after the prompt, and can outlast the answer by up to a minute while the approved tool runs. It is cleared when the turn ends (`agent/activity_tracking.py:132-154`; `agent/turn_facade.py:206-209`). Hermes Agent writes `last_activity_at` only together with the label, as the time of the touch that wrote it (`persistence/sqlite/conversation/_store/sessions.py:576-599`; `persistence/sqlite/workers/_lifecycle.py:131-132`). So the label counts only while it was saved no earlier than the running turn's newest tool call, and one of that call's tools has no result yet. A label that outlasts its approval is then never put on the model's next tool call, which would be announced as a new wait. The classic CLI's turns run in the gateway at v0.23.3, so its approvals take this path. The in-process prompt, which writes no label (`tools/approval.py:1144-1155`), is reached only by an agent that runs inside a CLI process; no path to it from `hermes chat` was found.
- **A one-time code.** When a site asks the browser vault for a one-time code in a chat whose app can show a code card, the gateway's wait for it touches the label as `waiting for a one-time code (Ns elapsed)`, saved as an approval's is (`gateway/session_vault_code_card.py:96-116`; `tools/browser_vault_tool.py:457`). It counts as a question, by the question label's rule. In a terminal, the TUI or the desktop app the code is asked for with no label (`gateway/session_vault_prompt.py:38-47`), so that wait shows as working.
- **When.** A wait's time is the tool call's row, which stays the same while the wait lasts, so one wait is never announced twice. Working's time is the lease's `acquired_at`, the turn's start.

## Status

Checked in this order, from the tip and the root's lease:

| Condition                                                                                                                                      | Status                 | Since                                |
| ---------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------- | ------------------------------------ |
| A field of the wrong type, or a newest row whose role is not `user`, `assistant` or `tool`                                                     | Unknown                | None                                 |
| Live lease, and a `clarify` call of the turn with no result                                                                                    | Needs you (question)   | The tool call's row                  |
| Live lease, and the approval label, saved since the turn's newest tool call, while a tool of that call has no result                           | Needs you (permission) | The tool call's row                  |
| Live lease, and the question label, likewise                                                                                                   | Needs you (question)   | The tool call's row                  |
| Live lease                                                                                                                                     | Working                | The lease's `acquired_at`            |
| A message kept as `content_refused`, of a turn taken back after a safety refusal, is newer than the newest row                                 | Failed                 | The refused turn's newest row        |
| Newest row is `assistant` with `display_kind` `failed_turn` and an `error`, or a `finish_reason` of `error`, `agent_error` or `content_filter` | Failed                 | The newest row                       |
| `ended_at` is set                                                                                                                              | Finished               | `ended_at`                           |
| Anything else, or no newest row                                                                                                                | Idle                   | The newest row, else the newest time |

- **Failed.** Hermes Agent closes a failed turn with an assistant row whose `display_kind` is `failed_turn` (`agent/turn_failure_copy.py:78`), with the error in `display_metadata`. The `finish_reason` values are those Hermes Agent counts as errors (`persistence/sqlite/conversation/_store/sessions.py:243-254`). An interrupt before any text gets the same row, usually with no `error`, so it shows as idle. A reply stopped after some text is marked `interrupted` (`agent/turn_api_call.py:210-212`) and shows as idle. From v0.23.1 a turn the model's provider refuses for safety gets no such row (`agent/conversation_loop.py:1923-1927`). Hermes Agent sets every row of that turn to `active = 0`, so the reply before it is the newest row again, and keeps the turn's message on screen as `content_refused` (`persistence/sqlite/conversation/_store/rewind.py:60-91`; `persistence/conversation/messages.py:89`). Such a message newer than the newest row is failed, until a later turn writes a row, from the newest row of its turn, so after any tool rounds the turn ran: the message and every row after it that is not `active` (`persistence/sqlite/conversation/_store/mutation_transcript.py:29-32`). A failed session stays failed once it is ended.
- **Finished.** Hermes Agent stamps a session it ends with `ended_at` and `end_reason`, and the first reason stands (`persistence/sqlite/conversation/_store/sessions.py:415-421`); `reopen_session` clears it (`:460`). The interactive CLI ends its session with `cli_close` on a normal quit and on Ctrl+C (`hermes_cli/cli_tui_runtime_mixin.py:547-560`; `cli.py:507-512`), through the gateway at v0.23.3 (`hermes_cli/cli_shutdown.py:159-163`). On SIGHUP or SIGTERM, as when its terminal closes, it leaves without ending the session (`hermes_cli/cli_tui_runtime_mixin.py:256-262`, `552-555`), and so does a CLI killed with `kill -9`, which cannot be caught (`cli.py:512`). The gateway then ends a session no client holds with `ws_orphan_reap`, `sessions.orphan_end_grace_s` after its last client went, 300 seconds unless set, or once its turn settles if that is later (`gateway/session_authority.py:455-457`; `gateway/session_viewer_close.py:199-215`, `242-269`; `hermes_cli/config_defaults.py:2263-2265`). A chat from a messaging app stays open between messages until a reset ends it (`persistence/sqlite/_schema_ddl.py:43`). `compression` is a step on, not an end, and the tip is never a row that ended with it unless every row did.
- **Idle against finished.** Neither the database nor anything the adapter reads says whether an open session's CLI or gateway still runs. The gateway writes no heartbeat row; only `tui_gateway` does (`tui_gateway/session_reaper.py:542`). While the gateway runs, it ends a session whose CLI has gone, as above. Hermes Agent also closes orphaned rows through the TUI gateway's startup sweep, of `tui`, `desktop`, `subagent` and `unknown` rows (`:462`, `496-498`), and through its auto-maintenance, which is off unless `sessions.auto_prune` is set (`session_retention.py:176-268`; `hermes_cli/config_defaults.py:2226-2228`). So a session left open by a killed gateway shows as idle, and as stale after a day.

## Names, folders and apps

- **Name:** the tip's title, else the root's, cleaned and cut as every agent's is. Hermes Agent's own list does the same, since a title moves from the root to the tip after a compression (`persistence/sqlite/conversation/_store/session_list.py:39-44`). Without a title, the folder's name, then the session's id. As the first turn starts, Hermes Agent writes the first line of the first message as the title, cut to 48 characters and marked `derived` (`derive_title` and `apply_instant_title`, `agent/title_generator.py:368-379`, `:771-791`), and then has a small model write one in its place (`auto_title_session`, `:794-847`). A title has a provenance, and only a higher one replaces it: `derived`, then `llm`, then `user` (`persistence/sqlite/_state/common.py:18-21`; `persistence/sqlite/_schema.py:251-256`). The model's call runs beside the turn, or, when it would reach the self-hosted server the turn is using, once the turn has ended (`title_upgrade_must_wait_for_turn`, `:205-231`). The first title stays while the call fails or gives nothing usable, and for good with `auxiliary.title_generation.model_upgrade_enabled` false (`maybe_auto_title`, `:899-973`). `title_source` says which a title is, so the query tests it inside SQLite and a title marked `derived` is not printed. Agent Lookout never holds its text, and the session takes the next name in line. The test is Hermes Agent's own rank (`_title_rank`, `persistence/sqlite/_schema.py:1853-1857`): `llm` and `user` pass, and so does a row with no `title_source`, which Hermes Agent cannot tell from a title typed before it kept the mark, so it ranks as `user`. Any other value ranks with `derived` and does not pass. `_has_upgraded_title` (`agent/title_generator.py:701-712`) reads such a value the other way, as a title that needs no model, but it only decides whether to make the call. The rank decides what may replace a title, and leaving a title out cannot show someone's words. `derived` also marks the model's `Friendly greeting` for a message with no topic (`agent/title_generator.py:829-830`) and the `<title> #2` of a branch the TUI or desktop app names itself (`tui_gateway/methods_session_branch.py:116-122`; `tui_gateway/methods_session_seed.py:84-87`), so those take the next name too. A title that passes goes where every session's name goes: [What a session's name can hold](../../PRIVACY.md#what-a-sessions-name-can-hold) says what that means for emails, webhook posts and pushes.
- **Folder:** the tip's `cwd`, else the root's. It is set for local CLI runs (`run_agent.py:44-55`), and for a gateway session from the folder the client sends when it makes it (`persistence/sqlite/authority/_local.py:77-82`, `90-99`). A child with no `cwd` takes its parent's (`persistence/sqlite/conversation/_store/sessions.py:343-346`). A chat from a messaging app has none.
- **App:** the terminal for `cli` and `tui`, and for `local` made by either; the desktop app for `desktop`, and for `local` made by it. Hermes Agent keeps its gateway's `cli`, `tui`, `gui` and `acp` sessions as `local`, with the surface in `created_source` (`gateway/session_policy.py:87-109`). Anything else, such as `acp`, a messaging platform, `api_server`, `webhook` or `cron`, is not known.
- **None of these:** a process ID, a link, Jump, Stop, Answer, token counts or `lastWriteAt`.

## Known gaps

- A session whose gateway was killed stays idle, and is stale after a day. One whose terminal was closed, or whose CLI was killed, while the gateway runs shows as idle, or as working while its turn goes on, until about 5 minutes after it went, or until its turn settles if that is later, and then as finished.
- A wait for an approval or a one-time code shows 10 to 70 seconds late, and can stay up to a minute after it is answered. A one-time code asked for in a terminal, the TUI or the desktop app writes no label, so that wait shows as working.
- A turn whose context overflows writes no closing row (`agent/conversation_loop.py:1923-1927`), so it shows as idle, not failed.
- A turn refused for safety whose message also held a compression's summary leaves that summary in the conversation, as its newest row (`persistence/sqlite/conversation/_store/mutation_transcript.py:33-35`), so it shows as idle, not failed.
- A remote gateway's sessions (`HERMES_TUI_GATEWAY_URL`) live in that machine's database, which Agent Lookout reads only by running there itself.
- A home with `HERMES_DATA_DIR_SUFFIX` is not read.
- Earlier reset segments of a local session are not folded into it.
- `kanban`, `tool` and `oneshot` sessions, and subagent runs, are not listed.
- Nothing is read on Windows, where Agent Lookout never runs `sqlite3`. A Hermes Agent inside WSL is not seen from Windows; an Agent Lookout inside WSL reads WSL's own `~/.hermes` as on Linux.
- With only a `sqlite3` that has the WAL-reset bug, Hermes Agent can switch a rollback-journal database to WAL mode between the look at its header and `sqlite3`'s open. The read is dropped once it is seen, but the open has happened, with `readonly_shm=1`. Installing a `sqlite3` that passes the test closes this.
- A WAL database with a live `-wal` is not read when every `sqlite3` found has the WAL-reset bug, as Ubuntu's and Debian's often do. Docker and OrbStack mounts keep the database in rollback-journal mode, which any `sqlite3` reads.
- A database in rollback-journal mode is not read while a `state.db-journal` that a write left unfinished holds a write to undo. It is read again once Hermes Agent opens the database and undoes the write.
- A `profiles/` folder that cannot be listed, or a profile's folder that cannot be looked at, is not told from one that is not there. Those profiles are left out until the list, made at most once a minute, works again. Their sessions are not listed and the card does not name them. While Agent Lookout runs no ended goes out for them, since `health.parts` names only the profiles read or found with no database. On the first poll after it restarts, a session of theirs the history kept gets an ended, as one of a profile deleted while it was stopped does, and nothing takes that back once the list works. When no profile still listed has a database, the card says there is no database.
- A profile the first poll after Agent Lookout restarts has no read of, one that could not be looked at or was not safe to read, one that no fit `sqlite3` could read, one laid out as a version Agent Lookout does not read, or one not reached for want of time that has no earlier read, is named in `health.notRead`. It is left out of that poll's compare with the history, and compared at the first poll that reads it instead. So a session of it that changed or ended while Agent Lookout was stopped gets its event at that poll. The same goes for such a profile on another machine, whose Agent Lookout names it in its own answer. An older Agent Lookout there names none, so a session of such a profile there still gets an ended on the first poll after this Agent Lookout restarts.
- Quiet for is never shown: every session of a profile is in one file.
- No token counts yet. Hermes Agent stores a session's totals, not its newest reply's request.
- Hermes Agent older than v0.21.6 is not read.
- A title made from a message is left out only while Hermes Agent's mark says so, and some copies of one carry another. `/branch` in the CLI or a chat writes `<title> #2` as `user`, whatever the parent's title was (`hermes_cli/cli_commands_mixin.py:785-809`; `gateway/slash_commands_session.py:1388-1390`, `:1434`), and so does the API server's `POST /api/sessions/{session_id}/fork` when the request names no title (`gateway/platforms/api_server.py:2785-2792`), a session imported from Claude Code or Codex is titled `Imported from <agent>: <first line>` as `user` (`hermes_cli/foreign_sessions.py:263-265`; `persistence/sqlite/authority/_mutation.py:135`), and `import_sessions`, which restores an export and moves a session between profiles, writes a title with no `title_source` (`persistence/sqlite/housekeeping/_portability.py:50-73`). All of these show.
- A compression carries a title to the new row with `set_session_title`, which marks it `user`, and puts `derived` back in a second write (`agent/conversation_compression.py:3156-3169`). A read between the two has the title. The next read does not, unless that write never lands: the read of the old mark and the write that restores it both swallow errors, and a process that dies between the two writes leaves the same. The row then stays `user`, the title stays the name, and no model's title can replace it (`persistence/sqlite/conversation/_store/titles.py:106`).
- Names reads Partly in Hermes Agent's row of What each agent can report in Sources and in the guide's table, since a session with no title from a model or a person takes its folder's name or its id. With `auxiliary.title_generation.model_upgrade_enabled` false, it keeps that name until a person titles it.

## What it never reads

- **Files and folders in the root and each profile's folder:** `.env`, `auth.json`, `config.yaml`, which can hold endpoint keys (`hermes_cli/config.py:769-775`), every OAuth or token file, `memories/` (`MEMORY.md`, `USER.md`), `SOUL.md`, `sessions/` and everything in it, `sessions.json` among it, `runtime/active_sessions.json`, `gateway.pid`, `gateway_state.json`, `logs/`, `checkpoints/`, `cron/`, `kanban.db`, `active_profile`, and any other file. The adapter's own code opens only the first 20 bytes of each `state.db`, and only `sqlite3` opens `state.db`, its `-wal` and `-shm`, and a `state.db-journal` that a write left unfinished. A session's own folder is looked in for a git repository, as every session's is, as [PRIVACY.md](../../PRIVACY.md#git-repositories) describes.
- **Tables:** every one but `sessions`, `messages` and `session_turn_leases`, beyond the names in `sqlite_master` and of their columns. So never `system_prompts`, `session_admissions`, `worker_executions`, `worker_receipts`, `async_delegations`, `gateway_routing`, `gateway_heartbeats`, `state_meta`, `session_model_usage`, `compression_locks`, `conversation_generations`, any `messages_fts` table, or the Telegram topic tables.
- **Columns of `sessions`:** never `system_prompt`, `system_prompt_hash`, `model_config`, `user_id`, `chat_id`, `chat_type`, `thread_id`, `display_name`, `origin_json`, `session_key`, `model`, `billing_*`, the cost and token columns, `handoff_*`, `compression_*`, `git_*`, `last_activity_description`, `last_activity_provenance` or `tool_names`. Of those, three keys of `model_config`, `session_key` and four prefixes of `last_activity_description` are tested inside SQLite, and print 0, 1 or nothing. `title_source` is tested there too, and never printed.
- **Columns of `messages`:** never `content`, `api_content`, `reasoning*`, `codex_*`, `tool_calls`, `tool_name`, `display_metadata` or `display_identity`. How many calls in `tool_calls` have no answer, and how many of those are to `clarify`, and whether `display_metadata` has an `error` key, are tested inside SQLite, and nothing of their text is printed.
- **Programs:** no `hermes` command, no request to Hermes Agent's gateway, no `ps` and no git command.

## What breaks when Hermes Agent changes

| Change in Hermes Agent                                                                                            | What the dashboard shows                                                        | Where to fix it                                       |
| ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------- | ----------------------------------------------------- |
| A column the probe asks for is renamed or dropped                                                                 | The card says the database is from a version Agent Lookout does not read        | `sessionRows.ts`                                      |
| The lease table, or its holder's form, changes (`agent/turn_facade_lease.py:340-343`)                             | Running turns show as idle, or a dead process's turn as working                 | `sessionRows.ts`, `processes.ts`                      |
| The waiting label's words change (`tools/approval_gateway_wait.py:87`)                                            | A session waiting for approval shows as working                                 | `sessionRows.ts`                                      |
| `last_activity_at` is written apart from the label (`persistence/sqlite/conversation/_store/sessions.py:576-599`) | A session waiting for approval shows as working, or an old label as a new wait  | `src/core/mapping/hermes-agent/hermesAgentMapping.ts` |
| `failed_turn` is renamed (`agent/turn_failure_copy.py:78`)                                                        | A failed turn shows as idle                                                     | `src/core/mapping/hermes-agent/hermesAgentMapping.ts` |
| `content_refused` is renamed (`persistence/conversation/messages.py:89`)                                          | A turn refused for safety shows as idle                                         | `sessionRows.ts`                                      |
| A new kind of child is listed as a conversation (`persistence/sqlite/_schema_ddl.py:35-59`)                       | Its sessions do not show                                                        | `sessionRows.ts`                                      |
| A new source is hidden from people (`persistence/conversation/sessions.py:131`)                                   | Its sessions show                                                               | `sessionRows.ts`                                      |
| The home or root rule changes (`hermes_constants.py`)                                                             | Hermes Agent is not found, or found with no database                            | `home.ts`                                             |
| `clarify` is renamed (`tools/clarify_tool.py:160`)                                                                | A session asking a question shows as working                                    | `sessionRows.ts`                                      |
| A new value of `title_source` (`persistence/sqlite/_state/common.py:18-21`)                                       | Its titles are left out, so those sessions take their folder's name or id       | `sessionRows.ts`                                      |
| `_title_rank` changes for none or an unknown value (`persistence/sqlite/_schema.py:1853-1857`)                    | A title ranked with `derived` shows, or one ranked above it is left out         | `sessionRows.ts`                                      |
| A title made from a message is written as `llm` or `user`, or with no `title_source`                              | It shows as the session's name, and goes where a name goes                      | `sessionRows.ts`                                      |
| A new role for a conversation's rows                                                                              | Sessions that end on it show as unknown                                         | `src/core/mapping/hermes-agent/hermesAgentMapping.ts` |
| The WAL-reset range changes (`hermes_cli/sqlite_runtime.py:23-30`)                                                | A live `-wal` is read, or refused, by a `sqlite3` Hermes Agent judges otherwise | `sqlite.ts`                                           |
