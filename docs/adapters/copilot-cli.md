# Copilot CLI adapter notes

These notes record what Agent Lookout reads from Copilot CLI, where each value comes from, and what breaks when Copilot CLI changes. When the adapter stops working, start here.

Written on 2026-11-23 from public material alone. Copilot CLI is GitHub's terminal coding agent, in its command `copilot`. Its own program is not open source, so the `copilot` program and its packages were never downloaded, unpacked, read, disassembled or run to write these notes, and no real session or `~/.copilot` folder was looked at. It was built from GitHub's docs, the MIT Copilot SDK v2.0.1 and open-source readers, never checked on a computer running Copilot CLI, and its card says so. What is here comes from:

- GitHub's docs, github/docs at `d7487f5` (2026-11-20), whose content is under CC-BY-4.0 and whose code is MIT (`LICENSE`, `LICENSE-CODE`). It has no release tags, so each citation names that commit. Cited as `docs:` and the file under `content/copilot/`.
- GitHub's MIT-licensed Copilot SDK, microsoft/copilot-sdk at tag v2.0.1 (`3ce6145`), copyright GitHub, Inc. (`LICENSE:1-3`). github/copilot-sdk now redirects there. Its `nodejs/src/cliVersion.ts:1` pairs it with Copilot CLI 1.0.114, the newest release when this was written. Cited as `sdk:`.
- Open-source readers of Copilot CLI's files, each under its licence and named with the commit read: getagentseal/codeburn at `c08d761` (MIT), github/awesome-copilot at `f10fdb8` (MIT, and `extensions/agent-radar` has an MIT licence of its own), microsoft/intelligent-terminal at `0fe4259` (MIT), codeaholicguy/ai-devkit at `210605a` (Apache-2.0), atuinsh/atuin at `86573ef` (MIT), jazzyalex/agent-sessions at `3dfa040` (MIT), muxy-app/muxy at `4466dee` (Apache-2.0) and dosu-ai/decant at `1966b2d`, v0.18.0 (Apache-2.0), whose Copilot fixtures are invented (`fixtures/copilot/README.md:1-5`). From them only facts and shapes were taken: names, fields and what they saw. No code was copied, and every fixture was written by hand.

Two sources were left out. kenn-io/agentsview at `07ed096` is MIT, but its own notes say some of its Copilot facts were checked against Copilot's published npm packages (`docs/internal/session-format-sources.md:1925-1940`). github/copilot-cli, whose changelog could date the layout's changes, gives no licence (NOASSERTION), so it was not read.

The code is in `src/collector/adapters/copilot-cli/`. `index.ts` builds the adapter, `home.ts` finds Copilot's folder, `sessionFolders.ts` finds the sessions, `locks.ts` reads the names of their locks, `eventsReader.ts` reads each event log, `records.ts` reads each line as bytes, and `toSession.ts` makes the session. The fold of a log is `src/core/mapping/copilot-cli/copilotCliFold.ts`, and the status `copilotCliMapping.ts` beside it. It walks each line with Muse Code's `src/collector/adapters/muse-code/jsonWalker.ts`, decodes its one folder and its times with Autohand Code's `literalOf` and `timeAt`, checks a folder with Pi's `folder`, takes its limits of 200 sessions and a sweep once a minute from Pi's finder (`src/collector/adapters/pi/sessionFiles.ts`), checks a lock's process with Qwen Code's `src/collector/adapters/qwen-code/processCheck.ts`, and keeps a wait across polls with DeepSeek Harness's `continuedDeepseekHarnessWait`.

## How it reads Copilot CLI, and why

It needs nothing installed and changes nothing. It reads each recent session's event log, read-only, as bytes, and the names of the locks beside it, and asks whether each lock's process runs. It runs no Copilot program and makes no request to Copilot or to GitHub.

GitHub documents no listing of sessions that an outside program can run: the CLI's reference gives `--json` only for its plugin, MCP, skill, instruction, LSP and config listings (`docs:reference/copilot-cli-reference/cli-command-reference.md:110-185,1062`). The SDK's `listSessions` and `sessions.checkInUse` need a running Copilot runtime, and `checkInUse` is marked experimental (`sdk:nodejs/src/generated/rpc.ts:40192-40214`). Hooks would need Agent Lookout's own code inside Copilot. So the files are read alone, as the Codex and Muse Code adapters do, and this adapter is expected to break when Copilot changes them. CONTRIBUTING's fourth step asks for the files to be checked against a listing the vendor documents for outside tools, and this adapter does not do that.

## Where it looks

Copilot keeps its configuration, session history, logs and customizations in one folder, `~/.copilot`, and `COPILOT_HOME` replaces that whole path (`docs:reference/copilot-cli-reference/cli-config-dir-reference.md:16,668-678`; `cli-command-reference.md:954`). On Windows it is `%USERPROFILE%\.copilot` (`docs:reference/hooks-reference.md:37`; `cli-config-dir-reference.md:451-455`), as Microsoft's reader also takes it (`intelligent-terminal:tools/wta/src/session_watcher/copilot_status.rs:26-34`). The folder read is the first that applies:

1. `AGENT_LOOKOUT_COPILOT_HOME`, trimmed, when it is not empty. A missing `session-state` in it is then an answer, not a missing Copilot, and it is looked for on every poll.
2. `COPILOT_HOME`, as Agent Lookout's own environment gives it, when it is not empty and a whole path on the system's rules. One that is not is passed over and the card says so, as Copilot would read it from the folder it was started in, which nothing here can know.
3. `.copilot` in the home folder.

The sessions are in `session-state` there. Nothing else is read for the place: not `--config-dir`, which is deprecated in favour of `COPILOT_HOME` (`cli-command-reference.md:712`), not any `XDG_*` variable, not `COPILOT_CACHE_HOME`, whose cache folder `COPILOT_HOME` does not move (`cli-config-dir-reference.md:680-685`), and not `config.json`, `settings.json`, `session-store.db`, `logs/` or `ide/`. Copilot moves older XDG locations to `~/.copilot` at start-up when `COPILOT_HOME` is unset, and the docs do not name those locations (`cli-config-dir-reference.md:436-449,459`). `COPILOT_HOME` is Agent Lookout's own: someone who sets it only in Copilot's shell, or gives a Copilot `--config-dir`, sets `AGENT_LOOKOUT_COPILOT_HOME`. When `session-state` is missing, it is looked for again once a minute.

## The sessions folder

`session-state/` holds the session history, organised by session ID in folders, each with its event log, `events.jsonl`, and workspace files, which make `--resume` and `--continue` work (`docs:reference/copilot-cli-reference/cli-config-dir-reference.md:619-621`). Copilot CLI and the GitHub Copilot app keep the whole record of each session there (`docs:concepts/security-governance-and-network-settings/session-data.md:38`). The SDK gives the layout as `~/.copilot/session-state/{sessionId}/` with `events.jsonl`, `workspace.yaml`, `checkpoints/`, `plan.md` and `files/` (`sdk:docs/features/session-persistence.md:527-544`), also as `COPILOT_HOME/session-state/{sessionId}` (`sdk:docs/setup/multi-tenancy.md:620,628`). Readers also saw `session.db`, `research/` and `rewind-file-snapshots/` in a session's folder, `.session-operation-locks/` beside the session folders and `detached-shells/*.json` (`agent-sessions:docs/guides/copilot-cli-local-history.html:125`; `atuin:crates/atuin-common/src/harnesstools/copilot/session.rs:218-220`; `awesome-copilot:extensions/agent-radar/README.md:81`), and the SDK's schema gives each session a SQLite database of its own (`sdk:nodejs/src/generated/rpc.ts:37905-37913`). Copilot first writes a session to disk when it handles its first message (`sdk:docs/features/session-persistence.md:7`), and one reader found 20 of 32 session folders with only `workspace.yaml` and other folders, no `events.jsonl` (`agent-sessions:docs/guides/copilot-cli-local-history.html:127`).

Everything from `session-state/` down is looked up with `lstat`, which follows no link, and a link, or anything but a folder or an ordinary file, is never gone into or opened, `session-state/` itself included. On each poll `session-state/` is looked up and listed again when its modified time moved, as it does when a session's folder is made. Only names that are a lowercase UUID, 8-4-4-4-12 hex, are taken: the older flat `<id>.jsonl` files, which one reader's guide dates to before 1.0.11 and its own notes to before 1.0 (`agent-sessions:docs/guides/copilot-cli-local-history.html:115,122-123`; `docs/agent-json-tracking.md:356`), dot names such as `.session-operation-locks/`, and the folders of sessions the SDK named with an ID of its own, are never looked up.

Each session folder not passed over is looked up, and then its `events.jsonl`, which must be an ordinary file. A session whose log, or folder, was changed in the last day is read, the newest 200 of them, and every session open or needing you at the last poll however old. Any other is passed over until the next sweep. A process makes its lock in the folder as it opens a session, which moves the folder's modified time, so a session opened in the last day counts though its log is older. A folder with no log yet is looked at again when its time moves, as it does when the log is made, while it was changed in the last day. Once a minute a sweep lists `session-state/` again and looks up every session folder. So a session not written for over a day before Agent Lookout started, and not opened since, is not listed until it is written again, and a session with no event log, before its first message, is not listed at all.

## The locks

The SDK says a session is in use while another running process holds it "via an alive lock file" (`sdk:nodejs/src/generated/rpc.ts:40192-40214`). Three readers agree that the lock is `inuse.<pid>.lock` in the session's folder (`ai-devkit:packages/agent-manager/src/harnesses/copilot/CopilotSessionLocator.ts:37,76-79,159-160`; `awesome-copilot:extensions/agent-radar/collector.mjs:46-47,492-498`, `README.md:80`; `intelligent-terminal:tools/wta/src/session_watcher/copilot_status.rs:95-121`). ai-devkit saw it on macOS and says it exists only while Copilot runs (`docs/ai/design/2026-06-09-feature-copilot-adapter-agent-manager-package.md:41,94-96`). agent-radar checks the process with signal 0. Microsoft's reader needs the process to have started before the lock last changed. One reader each says that the lock holds its process ID as text, that `inuse.<pid>.hold` is held open on Windows, and that a lock's name left behind proves nothing (`copilot_status.rs:106-107,146-165,232-235`), and that a Homebrew install runs a wrapper and a child, with the lock naming the child (`ai-devkit:docs/ai/design/2026-06-09-feature-copilot-adapter-agent-manager-package.md:99-101`).

So a session's folder is listed again only when its modified time moved, as a lock's making or removal moves it, or once a minute, and a listing that fails keeps the last one. Of its names only those that match `^inuse\.([1-9][0-9]{0,9})\.lock$` are kept, each looked up with `lstat`, which must say it is an ordinary file, and its modified time kept, as when the lock was made. A lock is never opened, and `inuse.<pid>.hold` and every other name in the folder, `workspace.yaml` among them, are never looked up or kept.

A lock counts when its process answers signal 0, which sends it nothing, and, on a Mac, when `ps -o pid=,lstart= -p <pids>` says that process started no later than a minute after the lock was made: a process that started later was given the ID after Copilot's ended, as after a crash. This is Qwen Code's check (`src/collector/adapters/qwen-code/processCheck.ts`), run every 30 seconds while a lock's process runs and sooner when another appears, and a `ps` that says nothing about a process leaves signal 0 to decide. Linux's `ps` works a start out again from the clock each time, so it moves when the clock is set, and Windows has no `ps`, so on both signal 0 alone decides, as for Grok Build and Kimi Code, and a session whose Copilot crashed can show as open while another program has its process ID. A session is held while at least one of its locks counts.

## The event log

The log is opened read-only, without following a link at its name and without waiting on a pipe, only when its `lstat` size, modified time or identity changed, and only when the open file is the one that `lstat` found. Its write time is the later of the `lstat`'s and the open file's.

Every event has the envelope `{id, timestamp, parentId, agentId?, ephemeral?, type, data}`, with `timestamp` in ISO 8601 and `agentId` absent for the main agent and for events of the session itself (`sdk:docs/features/streaming-events.md:50-62`; `sdk:nodejs/src/generated/session-events.ts:2408-2441`). An event marked `ephemeral` is "not persisted to the session event log on disk". In the two redacted real logs codeburn keeps, one from CLI 1.0.82 and one from VS Code's agent host, each line is one compact JSON object, its keys in the order `type`, `data`, `id`, `timestamp`, `parentId` (`codeburn:tests/fixtures/copilot/cli-store-session/events.jsonl:1`; `tests/copilot-agent-host.test.ts:1-3`; `agent-sessions:docs/guides/copilot-cli-local-history.html:137`). So `timestamp` comes after `data`, and a line is walked as a whole object, its keys in any order.

A resume appends to the same file (`sdk:nodejs/src/generated/session-events.ts:2654`). With `COPILOT_SESSION_EVENT_LOG_ROTATION_BYTES` set in Copilot's environment, Copilot archives the log as `events.N.jsonl` and puts a new `events.jsonl` in its place, which starts with a link to the one before and checkpoint events, and a repair of a damaged log can rewrite its start on the next write (`sdk:docs/features/session-persistence.md:170-215`; `decant:docs/sources.md:134-136`). So:

- The first time, and whenever the file is replaced, shrinks, grows by more than 8 MiB, or does not go on from the last line break read, it is read from its start: all of it up to 8 MiB, and past that its first 64 KiB, for its `session.start`, and its last 8 MiB, from the first line that begins there, with the lines between taken as a gap.
- After that, only the whole lines added are read, from where the last whole line ended, and a partial last line is held back until it ends.
- At most one piece of 256 KiB and one line's first 1 MiB are held at once. `events.N.jsonl` and every other file are never opened.

### Reading as bytes

A line is walked, as bytes, only when its first 1 MiB holds one of the types read in quotes, such as `"session.start"`. It is walked with Muse Code's walker, which steps through the JSON's syntax, compares each key byte for byte, and gives each wanted value as where its bytes are, and for an array whether it holds anything. Once `type` is read and is not one of these, the walk stops. Only these are read:

| `type`                                       | Read                                                                       | Source                                                                   |
| -------------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------------------ |
| `session.start`                              | `data.sessionId`, which must be the folder's name, and `data.context.cwd`  | `session-events.ts:2449-2554`; codeburn's 1.0.82 log, line 1             |
| `session.resume`                             | `data.context.cwd`, `data.continuePendingWork` and `data.sessionWasActive` | `session-events.ts:2654-2731`                                            |
| `user.message`                               | nothing more                                                               | `session-events.ts:6909`                                                 |
| `assistant.turn_start`, `assistant.turn_end` | `data.turnId` and `data.parentToolCallId`                                  | `session-events.ts:7600-7607,8932-8939`; `streaming-events.md:1025,1032` |
| `assistant.message`                          | whether `data.toolRequests` is an array that holds anything                | `session-events.ts:8382`; codeburn's logs                                |
| `tool.execution_start`                       | `data.toolCallId`, and `data.toolName` compared as bytes with `ask_user`   | `session-events.ts:10075-10091`                                          |
| `tool.execution_complete`                    | `data.toolCallId`                                                          | `session-events.ts:10377-10381`                                          |
| `permission.requested`                       | `data.requestId` and `data.resolvedByHook`                                 | `session-events.ts:12391-12411`                                          |
| `permission.completed`                       | `data.requestId`                                                           | `session-events.ts:13778-13794`                                          |
| `abort`                                      | nothing more                                                               | `session-events.ts:1151-1159`                                            |
| `session.task_complete`                      | `data.outcome`, compared as bytes with `completed` and `continue`          | `session-events.ts:798-807,6057-6086`; `agent-loop.md:178-213`           |
| `session.error`                              | nothing more                                                               | `session-events.ts:2822-2834`                                            |
| `session.shutdown`                           | `data.shutdownType`, `routine`, `error` or another word                    | `session-events.ts:579-583,4384`; `streaming-events.md:700-713`          |

Every line read gives `type`, `timestamp`, whether it has `agentId`, and whether its `data` has `parentToolCallId`. A line with either is a sub-agent's (`session-events.ts:7600-7603,8932-8935`; `awesome-copilot:extensions/agent-radar/collector.mjs:282`): its lifecycle lines, its messages and its replies are passed over, its turns are kept apart by `parentToolCallId` and `turnId`, and its tool calls and permission requests count as any agent's. Every other type is passed over: `model.*`, `session.usage_*`, `hook.*`, `system.*`, `subagent.*`, `session.info`, the compaction events and any type not known. The real logs hold types the SDK's schema does not, such as `model.*` and `session.usage_record` (`atuin:crates/atuin-common/src/harnesstools/copilot/session.rs:5-6`).

Only three kinds of bytes ever become text, each found as bytes first: the working folder, one JSON string of at most 16 KiB, by `literalOf`, kept only when it is a whole path of at most 4,096 characters with no control character; `timestamp`, from its digits and signs alone, by `timeAt`; and the IDs, 1 to 256 printable ASCII bytes each, as `latin1`, kept only as keys while their call, request or turn is open, and, for a `permission.completed` with no open request, until that request comes, at most the newest 256 of them. A user's message, a reply's content and reasoning, a tool's arguments and result, `permissionRequest` and `promptRequest`, which hold commands, diffs and file contents, an error's message, and every other field are stepped over as bytes and never turned into text, kept, shown or logged. The log holds prompts, tool calls, shell output and errors in plain text (`agent-sessions:docs/guides/copilot-cli-local-history.html:103,130-133`).

A line longer than 1 MiB is read as far as its first 1 MiB. A tool call's and a permission request's ID come first in its `data` in the real logs, so they stand. A user's message or a reply with no `agentId` in what was read is taken as the main agent's, and a reply whose `toolRequests` lie past the cut is not known to ask for tools or not. Any other line of a type read that is cut, broken, or missing a field it needs, and a `session.start` whose `sessionId` is not the folder's name, is unreadable.

### The fold

The fold keeps no bytes of the log, only IDs, times and flags. A main line has no `agentId` and no `data.parentToolCallId`.

- Each main `session.start` or `session.resume` begins a lifetime. At a `session.resume`, open permission requests, questions, tool calls and turns from before it are dropped unless `continuePendingWork` is true or `sessionWasActive` says the resume joined live work another client was running: Copilot keeps such work pending then, and otherwise normally marks it interrupted (`session-events.ts:2675-2678,2728-2731`; `agent-sessions:Resources/Fixtures/stage0/agents/copilot/small.jsonl:24`). agent-radar also keeps it while `alreadyInUse` is not written as false (`awesome-copilot:extensions/agent-radar/collector.mjs:291-303`), but the SDK says `sessionWasActive` is false or left out when the session had no live work, so the SDK's rule is followed.
- Open permission requests are kept by `requestId` with their time, from any agent, unless `resolvedByHook` is true, which means a hook already settled the request (`session-events.ts:12408-12411`). A `permission.completed` with the same `requestId` closes one, whichever was written first: the SDK's quick reference puts `permission.requested` before `tool.execution_start` and codeburn's 1.0.82 log has the opposite (`streaming-events.md:1006-1008`; `codeburn:tests/fixtures/copilot/cli-store-session/events.jsonl:100-103`), so pairs go by ID, never by order. A completion with no open request is kept until its request comes, the newest 256 of them, the oldest let go first, which also holds the completions of requests a hook settled.
- An `ask_user` call is open from its `tool.execution_start`, from any agent, until a `tool.execution_complete` with the same `toolCallId`. `ask_user` is the CLI's tool for asking you a question, and `--no-ask-user` turns it off (`docs:reference/copilot-cli-reference/cli-command-reference.md:739,900`). Two readers treat an open `ask_user` as a wait for you (`intelligent-terminal:tools/wta/src/session_watcher/classify_copilot.rs:3,60-83`; `awesome-copilot:extensions/agent-radar/collector.mjs:536`).
- Any other tool call is open until its completion.
- The main turn is open between a main `turn_start` and the `turn_end` with the same `turnId`, and notes whether any main reply in it had a `toolRequests` that holds anything. A sub-agent's turn is open until its own end.
- The newest main lifecycle line is kept: `user.message`, `turn_start`, `turn_end`, `abort`, `session.task_complete`, `session.error`, `session.shutdown`, `session.start` or `session.resume`.
- A main `session.task_complete` whose `outcome` is `completed` makes the open main turn one that asked for nothing more, as Copilot then ends the run with that turn. One whose `outcome` is `continue` leaves the turn as it was, and one with `blocked`, no `outcome` or another word leaves whether the turn asked for tools not known.
- An unreadable line makes the fold unsure until a lifetime begins afresh, and more than 256 permission requests, questions, tool calls and sub-agent turns open at once does too. The completions kept for a request to come never do. A gap drops everything open and leaves the main turn not known until a main turn line comes.

Each pass of Copilot's tool loop is one `assistant.turn_start` and `assistant.turn_end`, one message usually makes several, and the loop ends after a turn whose reply asks for no tools (`sdk:docs/features/agent-loop.md:19-39,80-98`). It also ends when the model calls the `task_complete` tool, as autopilot asks it to, and Copilot accepts the completion (`agent-loop.md:178-194`; `sdk:nodejs/src/toolSet.ts:130-132`). Copilot writes `session.task_complete` for such a call, whose `outcome` is `completed` when the completion was accepted, `continue` when it was rejected because more work remains and `blocked` when it cannot go on without intervention, and which has no `outcome` on older events and invalid calls (`session-events.ts:798-807,6070-6081`). The SDK gives a terminal tool as one reason a completion is accepted, and a completion tool that is withdrawn does not end a task (`session-events.ts:822-831`; `sdk:docs/features/task-analytics.md:122`). A turn runs the tools its reply asked for before its `turn_end` (`agent-loop.md:80-87`), so `session.task_complete` should come before its turn's end, and one that comes after is read the same way. In both of codeburn's real logs, each request's last `assistant.message` has `toolRequests: []` and is followed by `assistant.turn_end`, then `session.usage_checkpoint`, and every earlier turn asked for at least one tool (`codeburn:tests/fixtures/copilot/cli-store-session/events.jsonl:56-58,108-110`; `tests/fixtures/copilot/agent-host-session/events.jsonl:55-56,114-115`).

## Status

`session.idle` and `assistant.idle` are ephemeral and never written to the log (`sdk:nodejs/src/generated/session-events.ts:2899,8960`; `streaming-events.md:221,599`; `awesome-copilot:extensions/agent-radar/collector.mjs:307`), nor are `user_input.requested`, `elicitation.requested`, `exit_plan_mode.requested`, `auto_mode_switch.requested`, `session_limits_exhausted.requested` and `mcp.oauth_required` (`session-events.ts:14516,14578,14632,16639,15667,15957,14885`; `streaming-events.md:755-794,928-943`). `session.title_changed` is ephemeral too (`session-events.ts:2999`), so muxy's reading of it from a log is taken as not confirmed (`muxy:crates/muxy-app-core/src/agent_sessions/parse.rs:147-156`). Copilot's own sidebar shows idle, a turn in flight, an unread finished turn, stopped on an error or needs attention, resumable, needs permission and waiting for an answer (`docs:reference/copilot-cli-reference/cli-command-reference.md:280-292`).

The first row that holds:

| Row | When                                                                                                                                                                                                                              | Status    | Since                                                    |
| --- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------- | -------------------------------------------------------- |
| 1   | The newest main lifecycle line is `session.shutdown` of type `error`                                                                                                                                                              | failed    | that line's time                                         |
| 2   | The newest main lifecycle line is any other `session.shutdown`                                                                                                                                                                    | finished  | that line's time                                         |
| 3   | No lock counts                                                                                                                                                                                                                    | finished  | the log's or the folder's last change                    |
| 4   | The folder's locks could not be listed, or a line that would decide could not be read                                                                                                                                             | unknown   | none                                                     |
| 5   | A permission request has been open at least 1 second                                                                                                                                                                              | needs-you | the oldest such request's or open `ask_user` call's time |
| 6   | An `ask_user` call is open                                                                                                                                                                                                        | needs-you | the oldest such call's start                             |
| 7   | The newest main lifecycle line is `session.error`                                                                                                                                                                                 | unknown   | none                                                     |
| 8   | A main turn is open, the newest main lifecycle line is `user.message`, a `turn_end` of a turn that asked for tools or a `session.task_complete` whose `outcome` is `continue`, or a sub-agent's turn or another tool call is open | working   | the newest `user.message`'s time                         |
| 9   | Lines went unread and no main turn line came since, or the last turn's tool requests could not be read, or a `session.task_complete` did not say whether the run goes on, or no lifecycle line was read                           | unknown   | none                                                     |
| 10  | Anything else: the last turn asked for no tools, an `abort`, a `session.task_complete` whose `outcome` is `completed`, or only a start or resume so far                                                                           | idle      | that line's time                                         |

The 1 second of row 5 is Agent Lookout's own guard, not a fact of Copilot's: Copilot writes `permission.requested` even for a request it approves itself, and in the real logs those closed within 1 to 3 ms, while one person's answer took 4 min 46 s (`codeburn:tests/fixtures/copilot/cli-store-session/events.jsonl:100-103`; `tests/fixtures/copilot/agent-host-session/events.jsonl:26-27,37-38`). Microsoft's reader says Copilot writes the request while it waits (`intelligent-terminal:tools/wta/src/session_watcher/classify_copilot.rs:126-127`). A request's age is judged by its own time or by when Agent Lookout first saw it open, whichever says it is older, and one that waited at the last poll waits for as long as it is open, so a clock set back never turns a wait back into work. Rows 5 and 6 are one wait, on every request and call open in it, and a wait keeps the time it began for as long as any of what it waits on stays open. So a question and a permission open together are announced once, since the older, the reason is the permission while one waits, and a permission asked while a question waits is not announced on its own. A quick answer, within the second, may never show.

No timer ever turns working into idle, and the status text, `waitingText` and `waitingDetail` are never set, as Copilot's own words are in the fields that are never decoded.

`session.shutdown` is written only on a clean shutdown: when an IDE quits and kills a Copilot process it serves over ACP, the log ends with none (`codeburn:docs/providers/copilot.md:73-75,112-115`). A session can close while its process runs on: `/clear` closes the old session and fires `sessionEnd` with reason `user_exit` (`docs:reference/hooks-reference.md:370`), and the SDK's `sessions.close` writes the shutdown, writes what is pending to disk and lets go of the lock (`sdk:nodejs/src/generated/rpc.ts:40235`). One process can hold several sessions, and a local session stays active while its CLI runs, with no timeout (`docs:how-tos/copilot-cli/use-copilot-cli/work-with-multiple-sessions.md:158-164,170`). `abort` is written, with reason `user_initiated`, `remote_command`, `user_abort` or `autopilot_credit_limit`, and `session.task_complete` is best effort and may never come in interactive mode (`session-events.ts:1151-1159`; `streaming-events.md:874-880`; `agent-loop.md:198-213`). `session.error` is written with `errorType` and `message`, and when `eligibleForAutoSwitch` is true an ephemeral `auto_mode_switch.requested` follows (`session-events.ts:2822-2834`; `streaming-events.md:606-616`).

## Names and folder

A session's ID is its folder's name. In codeburn's real log, `session.start`'s `sessionId` is that name, a lowercase UUID (`codeburn:tests/fixtures/copilot/cli-store-session/events.jsonl:1`; `muxy:crates/muxy-app-core/src/agent_sessions/parse.rs:149-151`).

Its name is the last part of its working folder: `data.context.cwd` of the newest main `session.resume` that names one, else of the newest `session.start`, kept only when it is a whole path on the system's rules with no control character. With no folder, it is named `copilot-cli:` and its ID. Its start is the first `session.start`'s time.

`workspace.yaml` is never opened. It holds `id`, `cwd`, `git_root`, `repository`, `host_type`, `branch`, `name`, `client_name`, `user_named`, `summary_count`, `created_at`, `updated_at`, `remote_steerable` and `mc_*` fields (`sdk:nodejs/src/generated/rpc.ts:47624-47700`). No event names a session: Copilot makes a name at the first prompt and writes it there as `name`, with `user_named` set when `--name` or `/rename` chose it (`atuin:crates/atuin-common/src/harnesstools/copilot/session.rs:37-39`; `docs:reference/copilot-cli-reference/cli-command-reference.md:619,738,755`). A real file's shape shows `name` holding the whole first prompt word for word, with `user_named: false` (`agent-sessions:AgentSessionsTests/SessionParserTests.swift:5335-5350`), and a name given with `--name` or `/rename` is typed by you, so neither is read.

Its app is unknown. `client_name` in `workspace.yaml` tells Copilot CLI (`github/cli`) from VS Code's agent host (`vscode-agent-host`), and one reader maps `github/autopilot` to the Copilot app (`agent-sessions:AgentSessionsTests/SessionParserTests.swift:5335-5346`; `codeburn:docs/providers/copilot.md:42-48,73-75`; `awesome-copilot:extensions/agent-radar/collector.mjs:538`). VS Code's agent host and ACP hosts such as JetBrains write to the same `session-state/`, so their sessions show as Copilot CLI's. A second step could read that one line.

## Quiet for, tokens, Jump, Stop and Answer

Quiet for is the time since the log was last written, while the session works. A long command may write nothing until it ends. Tokens are on lines that are stepped over unread. No Jump: nothing read names a session's terminal or window. No Stop: a lock names a process that can hold other sessions too. No Answer: Agent Lookout makes no request to Copilot.

## On Windows

Copilot's folder is `%USERPROFILE%\.copilot`, as GitHub documents. `ps` is not run, so a lock counts while a process with its ID runs, by signal 0 alone, and a session whose Copilot crashed can show as open while another program has that ID. Microsoft's reader checks that the program is `copilot.exe`, which needs a process's name, and this adapter does not ask for one.

## What breaks when Copilot CLI changes

- GitHub documents `session-state`, `events.jsonl` and `workspace.yaml`, not the event format itself, and the SDK's schema is generated and changes with each runtime. A type renamed or a field moved is passed over, or makes the session unknown.
- A lock renamed, moved or no longer made: every session shows as finished.
- `session.idle` written to the log: nothing changes, as it is not read.
- A request for approval that waits in a way not written, as plan approval, MCP prompts and sign-ins, an auto-mode switch after a rate limit and a session-limit prompt are now: it never shows as needing you. It shows as working or idle, or as unknown after the rate-limit `session.error` that comes before an auto-mode switch.
- `COPILOT_HOME` or the place of `session-state` changed: the card says Not found.
