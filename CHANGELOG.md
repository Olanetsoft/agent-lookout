# Changelog

Changes that a user of Agent Lookout would notice, newest first.

## Unreleased

### Added

- Continue sessions, from its `cn` command and its VS Code and JetBrains extensions, read from the list in `~/.continue/sessions`, on macOS, Linux and Windows. A session always shows as unknown, since Continue writes nothing that says a session runs and `ps` shows `cn` only as `node`, and it never shows as working, needing you or finished. A tool call waiting for approval is written as one a crash left behind is, so it is not read, and a session's own file is never opened. A session is named after its folder, as Continue's title can be a line of your first prompt, and is listed for a day after its file was last written. It needs no program of Continue's, and no oldest version is named. Built from Continue's source at v1.5.45, and not yet checked on a computer running it. (#42)
- Crush sessions, for Crush v0.25.0 or later, read with `sqlite3` from `.crush/crush.db` in the newest 20 folders of Crush's list of projects, `~/.local/share/crush/projects.json`, on macOS and Linux. A session is named after its folder, and shows as unknown while a Crush program runs and as finished once none does, since nothing ties a session to a process, so it never shows as working or as needing you. Built from Crush's source at v0.99.0 and not yet checked on a computer running it. (#39)

## 0.2.19 - 2026-11-04

Goose, Pi and Kimi Code sessions show, a Hermes Agent session no longer takes a title made from your first message, and a running Mistral Vibe session no longer shows as finished when a read of its lease fails after one that worked, but for two rare cases.

### Added

- Goose sessions, for Goose v1.34.0 or later, read from its database, `~/.local/share/goose/sessions/sessions.db`, with `sqlite3`, on macOS and Linux. A session shows as unknown while a Goose program runs and as finished once none does, since nothing ties a session to a process, so it never shows as working, idle or needing you. A session finishes only when the last Goose program quits, which finishes every session at once and sends no Finished. It is named after its folder, or by a name you gave it or an ACP client sent: Goose's own title can be the first four words of your first prompt, and is never read. Agent Lookout keeps its ID, folder, times and that name, and never reads a message. This was built from Goose's source at v1.57.0, and has not yet been checked on a computer running Goose. (#38)

- Pi sessions, read from the file Pi keeps for each in `~/.pi/agent/sessions`, on macOS, Linux and Windows. A session shows as unknown while a `pi` program runs and as finished once none does, since nothing ties a session to a process, so it never shows as working, idle or needing you. A session finishes only when the last `pi` program quits, which finishes every session at once and sends no Finished. On Windows it stays unknown. It is named after its folder, or by a name it was given, such as with `/name`: Pi gives a session no name of its own. Agent Lookout keeps its ID, folder, start time and that name, and never turns a prompt, a reply or a tool's output into text. This was built from Pi's source at v1.5.0, and has not yet been checked on a computer running Pi. (#36)

- Kimi Code sessions, read from `~/.kimi-code`. A session shows as working from the lock Kimi Code keeps while it is busy, as needing you while it waits for your approval or an answer, and as failed when its last turn failed. A session whose subagent waits for you shows as working, since a subagent's wait is in its own file. Kimi Code keeps no lock on an idle session, so one shows as idle only once Agent Lookout has seen it busy, while that process runs, and any other as finished. Kimi Code before 2.3.0 keeps no lock at all, so with it every session shows as finished or failed. It is named after its folder, or by a title you, a client or Kimi Code's model set: its default title is the start of your first prompt, and is never kept. Agent Lookout keeps its ID, folder, times, process ID and which kind a wait is, and of the session's event file reads the last 1 MiB, and turns only the lines that ask or answer into text. This was built from Kimi Code's source at 2.4.1, and has not yet been checked on a computer running Kimi Code. (#32)

### Fixed

- Qwen Code's card in Sources lists the rest of what runs for Jump, whether or not anyone presses it. On a Mac, Tab check, `ps -A -o pid=,ppid=,tty=,comm=`, finds a session's tab of Terminal or iTerm2, once for each new process, every 5 seconds at most. One look can serve Claude Code and Qwen Code, so it shows on the card of each whose session it was for, and a look for a Claude Code session alone leaves Qwen Code's at "not run". On Linux with tmux, Jump check, `ps -o pid=,lstart= -p <pids>`, confirms a process found in a pane before its session gets Jump, every 30 seconds while a session's process is in a pane, and sooner when another is found in one. On a Mac that answer comes from the `ps` of Process check, so there is no Jump check. Each says "not run" until it has been asked, and Tab check stays so with `AGENT_LOOKOUT_TERMINAL_JUMP=off`. Without tmux or with `AGENT_LOOKOUT_TMUX=off` there is no Jump check, and Windows lists neither. Listing these adds no run of `ps` (#275).

- After one failed read of a Mistral Vibe session's lease, as when Agent Lookout is out of file handles, a session whose Vibe then goes no longer stays as working until it leaves the list. The failed read was remembered until the file changed, and the file does not change once Vibe has gone, so nothing asked whether its process still ran. A lease that cannot be read is now tried again every 30 seconds, and a session whose Vibe went shows as finished at the first read that works (#271).

- A running Mistral Vibe session no longer shows as finished, or sends Finished, when a read of its lease fails after one that worked, but for two cases below. A read that failed gave no time, so it counted as a lease just taken, for up to 30 seconds. Now a poll that cannot list `active/` or look a `.lock.json` up keeps the last read of it, and a `.lock.json` that changed and cannot be read keeps the time of its last read and gives no process. A failed look leaves a session as its last read shows it, a wait included. A poll that cannot list `active/` leaves out a session Vibe last wrote to more than a day ago, which only its lease keeps listed, until a listing works. Otherwise a listed session shows as open, with no wait, until a read works. That goes for one that showed as finished too, which sends Finished again if no program goes on to hold it. A lease with no last read to keep still counts as just taken: one that has never been read, which sends nothing unless `active/` was found missing first, and one whose last read went when `active/` or its `.lock.json` was found missing, which can send Finished if its session showed as open. A session another Vibe takes just as the last one goes, while its `.lock.json` cannot be looked up, shows as finished, and sends Finished, at least until a look works. A session whose Vibe went still shows as finished, at the first read that works at the latest (#282).

### Changed

- PRIVACY.md and the guide now say plainly what a session's name can hold. An email, a webhook post or a push holds no prompt, but it holds the session's name, which is the agent's own title and can echo what you first asked. [What a session's name can hold](PRIVACY.md#what-a-sessions-name-can-hold) says how for each agent: most titles are a model's, and a few can repeat your first words (#270).

- A Hermes Agent session no longer takes the title Hermes Agent writes from the first line of your first message, so those words no longer go into a notification, an email, a webhook post, a push or the history. Hermes Agent marks that title `derived` in `title_source`, and `sqlite3` leaves it out of what it answers, so Agent Lookout never reads it. The session shows its folder's name, or its ID when it has no folder, as with a chat from a messaging app, until a model or you name it, and for good with `auxiliary.title_generation.model_upgrade_enabled` set to false. A title from a model or from you stays, and so does a title with no `title_source`, which Hermes Agent ranks as yours. A copy Hermes Agent marks otherwise, such as the `<title> #2` of `/branch` in the CLI or a chat, still shows, as [What a session's name can hold](PRIVACY.md#what-a-sessions-name-can-hold) says. This was built from Hermes Agent's source at v0.22.5, and has not yet been checked on a computer running it (#281).

## 0.2.18 - 2026-11-04

Cline and OpenCode 2 sessions show, OpenCode 1.x, Qwen Code and Mistral Vibe sessions show when they ask you a question, and Jump reaches Qwen Code sessions.

### Added

- Cline sessions, from the sessions folder of its newer runtime, which its CLI, its desktop app and the VS Code builds that run it write: working, needing you while Cline waits for a tool's approval, idle, failed or finished, named after its folder. Agent Lookout reads the manifest Cline keeps for each session in `~/.cline/data/sessions`, at most 1 MiB and only when it changes, and keeps its status, times, folder and process ID. It never keeps the prompt, or Cline's title, which is by default the first line of the prompt, and never opens the session's messages file, whose time alone it looks up: Quiet for goes by the newer of that and the manifest's. A session whose manifest still says it is open is finished once its process has gone, and a session in Cline's hub stays idle after you close it, while the hub runs. A question Cline asks you shows as working. A session resumed in a new process with no new prompt keeps the process ID before it, so once that one has gone it shows as finished while it runs. On a Mac `ps` tells a process given a crashed session's ID from the session's own. On Linux and Windows such a session keeps the status its manifest last gave until that program ends, or, if it was idle, until it leaves the list a day after it was last written. The older VS Code extension's tasks are not read. It was built from Cline's source at cli-v3.0.74 and has not yet been checked on a computer running Cline. (#34)

- A Mistral Vibe session's details give the token counts of its newest reply, as Codex, Antigravity and Qwen Code sessions' do, such as `12,000 in, 340 out`, with how much of the input came from a cache when Vibe wrote more than 0 for it, since it writes 0 for a provider that sent none. Agent Lookout reads them from `session.contextUsage` in the public state it already reads for the status, so it opens no new file, and keeps three numbers of it. They are the newest reply's alone: the running total beside them is never read. A reply with no counts leaves those of the reply before it, and after Vibe compacts a conversation the details show a dash until the next reply. After a `/rewind` in place the counts show a dash until the next turn starts, and from then until the next reply they can be those of a reply the rewind took back. What each agent can report now says Yes for Tokens for Mistral Vibe. (#257)

- A Mistral Vibe session shows as needing you, as Waiting for permission or Asked you a question, while Vibe waits for your approval or an answer: from the record Vibe adds to the session's journal as it asks until the one it adds once you answer, decline or stop the turn. Its wait works as any agent's does, in the Needs you panel, notifications, email, webhook posts, pushes, Waits and Keep awake. Of what Vibe asks, Agent Lookout keeps only which of the two it is and when Vibe asked, never a tool's arguments, a question or your answer. A session that closes while it waits is finished, and so is one whose Vibe was killed. A question a killed Vibe left open on disk does not count once another Vibe program has the session, and neither does a callback left open by an earlier turn. A wait keeps the Mac awake for as long as it is listed, so on a Mac, while a session waits, Agent Lookout asks `ps` when the process its lease names started, and a process given a crashed Vibe's ID leaves the session finished. Linux and Windows make no such check, so there such a wait stands until that program ends, unless Agent Lookout found its process gone first and still remembers that. A session whose subagent waits for you still shows as working, since a subagent's wait is in its own files. What each agent can report, in Sources, says Partly for Mistral Vibe's Needs you. Sessions of Vibe 3.0, whose newer store format showed them with no status, now show their status too, since the formats up to Vibe 3.0.4's read as before. This was built from the source of Vibe 2.26.1 and 3.0.4 and has not yet been checked on a computer running Vibe (#70).

- Jump works for a Qwen Code session in tmux and in a tab of Terminal or iTerm2 on a Mac, as it does for Claude Code: it selects the session's pane, or brings its tab forward. Agent Lookout finds the place from the process ID in the session's record, with the same look at tmux and `ps` that serves Claude Code's sessions, so neither agent's sessions lose their Jump while the other's are listed. Qwen Code records no start time for its process on a Mac or Windows, so before it gives a session Jump, Agent Lookout asks `ps` when the process started, every 30 seconds: on a Mac about every open Qwen Code session, and sooner when another appears, and on Linux about a process found in a pane, and sooner when another is found in one. A session whose process started more than a minute after Qwen Code recorded it, as one given a crashed session's process ID does, gets none. `AGENT_LOOKOUT_TMUX=off` and `AGENT_LOOKOUT_TERMINAL_JUMP=off` turn it off for Qwen Code too, and What each agent can report, in Sources, says Partly for Qwen Code's Jump. This was built from Qwen Code's source at 0.25.1 and has not yet been checked on a machine running it (#186).

- A Qwen Code session shows as needing you, as Asked you a question, while Qwen Code 0.25.1 or newer asks you a question or to approve a plan: from the reply that calls `ask_user_question` or `exit_plan_mode` until the results Qwen Code writes once you answer, decline or press Esc. Its wait works as any agent's does, in the Needs you panel, notifications, email, webhook posts, pushes, Waits and Keep awake. Of the call Agent Lookout keeps only which of the two tools it is, never the question, the plan or your answer. With an older Qwen Code such a session still shows as working, since its files do not tell a reply that asks from one stopped with Esc, whose call never runs. A wait for a tool's approval still shows as working, since Qwen Code writes nothing while it asks. What each agent can report, in Sources, says Partly for Qwen Code's Needs you. This was built from Qwen Code's source at 0.25.1 and has not yet been checked on a machine running it (#185).

- An OpenCode 1.x session's details give the token counts of its newest reply, as Codex, Antigravity and Qwen Code sessions' do, such as `2,400 in, 150 out`, with how much of the input came from a cache when OpenCode wrote more than 0 for it, since it writes 0 for a provider that sent none. Agent Lookout reads them inside the query of sessions each poll already asks of OpenCode's database, as six numbers of the newest reply's `$.tokens` and nothing else of that message, and keeps three. In is the whole prompt, what was written to a cache included, and Out is what the reply wrote, its reasoning included, counted once whichever provider OpenCode uses. A reply still being written leaves the counts of the one before it, and so does one that ended with none, such as one stopped with Esc before the provider sent them, or a command run with `!`. A subagent's reply is never the one counted, and a reply further back than the session's newest 10 messages is not looked for. What each agent can report, in Sources, says Partly for OpenCode's Tokens: yes for OpenCode 1.x, none for OpenCode 2. `GET /api/sessions` gives them as `tokens`, and no event, history, email, post, push, `agent-lookout mcp` answer or `agent-lookout status` holds them. This was built from OpenCode's source at v1.19.0 and has not yet been checked on a computer running it (#191).

- A Gemini CLI session's details give the token counts of its newest reply, as Codex, Antigravity and Qwen Code sessions' do, such as `1,200 in, 120 out`, with how much of the input came from a cache when Gemini CLI wrote more than 0 for it, since it writes 0 for a count the API did not send. Agent Lookout reads them from the same read of the session file that gives its status, and keeps three numbers of the reply's `tokens` and nothing else of the line. Out is what the reply wrote, its thinking included, counted once: Gemini CLI writes the thinking apart, and Agent Lookout adds it. The lines are replayed as Gemini CLI replays them, so a reply taken back with `/rewind`, a declined tool or a stopped request is never the one counted. A subagent's file is never read for them, and a newer reply that has none leaves the counts as they were. What each agent can report, in Sources, says Yes for Gemini CLI's Tokens. `GET /api/sessions` gives them as `tokens`, and no event, history, email, post, push, `agent-lookout mcp` answer or `agent-lookout status` holds them. This was built from Gemini CLI's source at v0.64.0 and has not yet been checked on a machine running it (#177).

- Gemini CLI sessions run under macOS Seatbelt, as `gemini --sandbox` runs them on a Mac, show with no setting. Gemini CLI keeps those in `~/.cache/.gemini` instead of `~/.gemini`, and on a Mac Agent Lookout now reads that folder's `tmp/` beside the other's, in the same way, so `AGENT_LOOKOUT_GEMINI_CLI_HOME` no longer has to name it. A session there has an id of its own, `gemini-cli:<session ID>.<hash>.seatbelt`, never that of a session in `~/.gemini`, whose ids are as before. Gemini CLI shows as not found only while neither folder holds `tmp/`, and while one does, the other costs one look a poll. With `AGENT_LOOKOUT_GEMINI_CLI_HOME` set, only the folder it names is read. Gemini CLI's card in Sources names both folders. This was built from Gemini CLI's source at v0.64.0 and has not yet been checked on a Mac running it under Seatbelt (#179).

- A Gemini CLI session shows as failed when a request fails, from the time of the error Gemini CLI records, and as working again from your next prompt, and it sends what any session that fails sends. Gemini CLI records every error it shows the same way, so Agent Lookout knows a failed request's by how its text begins, compares that while the line is read, and keeps none of the text. Any other error, such as a slash command's, leaves the session idle, and a request that fails under `gemini -p`, or that needs you to sign in again, records no error. What each agent can report, in Sources, says Partly for Gemini CLI's Failed. This was built from Gemini CLI's source at v0.64.0 and has not yet been checked on a machine running it (#176).

- An OpenCode 1.x session shows as needing you, as Asked you a question, while OpenCode asks you a question or, in its experimental plan mode, to approve a plan: from the `question` or `plan_exit` tool call until you answer, decline or press Esc. Its wait works as any agent's does, in the Needs you panel, notifications, email, webhook posts, pushes, Waits and Keep awake. OpenCode writes nothing while it asks, so a question left unanswered for a day leaves the list, as any OpenCode session does a day after it was last written, and comes back once you answer. Of the call Agent Lookout tests only the tool's name and state, inside SQLite, and reads when it began, never the question or your answer. A wait for a tool's approval still shows as working, since OpenCode keeps it in memory. This was checked in OpenCode's source at v1.19.5 and has not yet been checked on a computer running it (#190).

- OpenCode 2's sessions show, from its table `session_v2` in the same `opencode.db`, whether OpenCode 1.x, OpenCode 2 or both wrote that file: each root session once, by its title, or else its slug, and its folder, as working while a turn runs, then idle or failed. For a session in both tables the `session_v2` row wins, so a 1.x session OpenCode 2 copied and carried on shows what OpenCode 2 wrote. Nothing there marks a session closed, and OpenCode 2's background service outlives its window, so a session shows as idle until `ps` shows no OpenCode program, and Agent Lookout now also knows the other names OpenCode 2 and that service go by: `opencode.exe`, `opencode2` and `opencode-cli`. ### Fixed

- A Mistral Vibe session whose Vibe crashed no longer shows as open because another program was given its process ID. On a Mac it shows as finished: Agent Lookout compares when the process started with when the session's lease was taken, once Vibe has written nothing to the session for a minute. Sources says when `ps` runs. On Linux and Windows a session stays finished while Agent Lookout remembers finding its process gone, which a restart forgets, and one whose process ID went to another program before that stays as it is, since neither a start time nor a program's name is sure there (#258).

- Gemini CLI's card in Sources says when a subagent's folder or file cannot be looked up, with how many sessions that touched and whether permission was refused or the lookup failed, since such a session can look quiet while a subagent works, and in the Mac app Keep awake can stop counting it. Quiet for then counts from the last write Agent Lookout saw, and the session stays listed. The card names no session, folder or file, and the note goes at the first look that works. A session with no subagent folder shows and costs what it did. This was built from Gemini CLI's source at v0.64.0 and has not yet been checked on a machine running it (#262).

- A wait no longer goes on counting in Waits after its session has left the list. When a poll leaves out a session in a wait, as OpenCode's reading while it is closed leaves out one past the day's cutoff, or as another machine that stops answering does, Waits stops at the last poll that listed the session, and stays there through a restart. A way of reading can leave out a session that still waits, so that alone is not taken as the wait's end: nothing goes in the Events log and nothing is sent. If the session is seen still waiting, it is one wait and the time out of the list counts, unless its agent gives a status time later than that last poll, which Waits counts as a new wait from that time. If a way shows it answered, or the way that last listed it shows it gone, the Events log says so then, and the wait counts only up to that last poll, in Waits, the Events log's line, the Timeline and Waited on you (#255).

- A Qwen Code session whose Qwen Code crashed shows as finished on Linux and on a Mac once another program is given its process ID. Before, it showed as open, often as working or needing you, for as long as that program ran. On Linux Agent Lookout compares the start token Qwen Code writes in the session's record with that program's, made from this boot's ID and one field of its `/proc/<pid>/stat`, every 30 seconds, as Qwen Code does, and no longer lists a record Qwen Code wrote in a container with process IDs of its own, or one Qwen Code wrote on a Mac or Windows into a folder it shares with Linux, as Qwen Code's own listing does not. On a Mac it asks `ps` when that program started, every 30 seconds, for every open Qwen Code session, not only one in a pane or a tab, and the same answer gives Jump. When neither can say, the session stays as it was. On a Mac, a session shows as finished while it runs if the clock was set back by more than a minute as its Qwen Code started, until it is restarted. Windows has neither, so there such a session still shows as open. Qwen Code's card in Sources gives the check and how often it runs. This was built from Qwen Code's source at 0.25.1 and has not yet been checked on a machine running it (#183).

- A wait that ends when Antigravity closes now ends there, in Waits and the Events log. A chat that needed you when the app closed could go to finished with no event, so Waits went on counting it for as long as the app stayed closed, and Events never showed the wait ending. If the chat still waits when the app opens, that is a wait of its own, and the time closed counts for neither (#251).

- A Gemini CLI session no longer looks quiet while a subagent it started works. A subagent writes to a file of its own, and the session writes nothing to its file while it waits, so its [Quiet for](docs/GUIDE.md#quiet-for) kept growing as if it had stopped. It now goes by the newest of the session's file and its subagents' files, in `chats/<session ID>/` in either of Gemini CLI's folders, and Keep awake counts those writes too. Agent Lookout only looks up when those files were last changed, for the sessions it lists, and never opens them. Sources says so. This was built from Gemini CLI's source at v0.64.0 and has not yet been checked on a machine running it (#178).

- Claude Code's card in Sources says what it runs `ps` for. Process check, `ps -o pid=,lstart= -p <pids>`, tells a session's process from another program given its process ID, every 30 seconds while a session's process runs, and sooner when another appears. On a Mac, Tab check finds a session's tab of Terminal or iTerm2. Stop check confirms a session's process when you stop it. Each says "not run" until something has asked, and on Windows, which has no `ps`, Process check says signal 0 alone. Listing these adds no run of `ps` (#256).

- The cards of Claude Code and Qwen Code in Sources list tmux and its `ps`. Pane check, the `tmux -u list-panes -a` that finds a session's pane for Jump, runs every 30 seconds while a session's process runs, and sooner when another appears or a Jump finds its pane gone. Pane parent check, the `ps -A -o pid=,ppid=` that follows a session's process up to a pane, runs with it while tmux lists a pane. Each says "not run" until it has been asked about one of that agent's sessions, and one run can serve both agents, so it then shows on both cards. On Windows, without tmux and with `AGENT_LOOKOUT_TMUX=off`, neither is listed. Listing these runs neither. To say whether tmux is there, Agent Lookout looks for its program every 30 seconds, which starts nothing (#263).

## 0.2.16 - 2026-11-02

Qwen Code sessions show what they last said, the Mac app's Keep awake card says which sessions keep the Mac awake right now, Hermes Agent's databases are read more safely, and a few things you meet with the keyboard or on a phone work as they should.

- Find a session from the keyboard. `/`, or `Cmd+K` on a Mac and `Ctrl+K` elsewhere, or the magnifier in the header opens a search over each session's name, folder, branch and agent, with every word typed found in any order. Sessions that need you are listed first, longest wait first, then the rest in the order of the Sessions list. Up and Down move through them, and Enter presses the session's Jump when it has one, or takes you to its row on the Overview. `?` lists every shortcut, including the arrow keys the charts, the Timeline and the switches already had.
- Open a session to see everything Agent Lookout knows about it. Click its row in the Sessions list or its card on the board, or move to its name with Tab and press Enter, and its details open over the Overview: its status with the reason and how long, its agent, app, full folder path, branch, start time and process ID, how many times and how long it waited for you, its own events and its row of the Timeline, with its Jump button where it has one. Each session's details have their own address, so a bookmark, a reload and the browser's Back button land on them, and closing them puts focus back on the row or card.
- A session that needs you opens its details from its name in the Needs you panel, and Enter in the search opens the details of a session with no Jump button.

#### Jump

- A Jump button opens a Claude Code session that runs in VS Code.
- A Claude Code session that runs inside tmux has a Jump button too. It selects the session's pane, the pane's window and, on any attached terminal that is showing another tmux session, the pane's session. The row says what happened: Selected in tmux, That pane has closed or tmux has stopped. It does not bring your terminal to the front. `AGENT_LOOKOUT_TMUX=off` stops Agent Lookout running tmux, and takes the button off sessions in tmux.
- On a Mac, a Claude Code session in a tab of Terminal or iTerm2, outside tmux, has a Jump button too. It brings that tab to the front, in its window, with the app. The first time, macOS asks once whether the program Agent Lookout runs in may control the app, and the row says so while it asks. If macOS did not allow it, the row says where to allow it: System Settings, Privacy & Security, Automation. Sessions in other terminals, such as Warp, Ghostty or the VS Code terminal, have no button. `AGENT_LOOKOUT_TERMINAL_JUMP=off` stops Agent Lookout looking for tabs of Terminal and iTerm2, and takes the button off sessions there.

#### Notifications

- Turn on notifications in Settings, and your browser shows a system notification when a session starts waiting for you. It names the session and the reason, and is cleared when the session moves on.
- With notifications on, Agent Lookout goes on sending them on a Mac after the dashboard tab is closed, for as long as it keeps running. It shows those itself, so they come from Script Editor and stay until you clear them. An open tab that is polling and Agent Lookout do not both send one for the same wait. `AGENT_LOOKOUT_NOTIFICATIONS=on` turns these on from the moment it starts, without the dashboard being opened.
- Choose what sends a notification. While notifications are on, Settings lists four events, each with its own switch: Needs you, Finished, Failed and Ended, which is a session leaving the list without having finished or failed. Needs you is on and the others are off until you change them. A notification names the session and what happened, and one that says Finished, Failed or Ended stays until you clear it. The choice is kept in the browser, and Agent Lookout's own notifications, with no tab open, follow it too. Nothing is sent for what was already true when the page opened or Agent Lookout started.

#### Email and webhooks

- Agent Lookout can email you when a session has waited for you for a minute, or as long as `AGENT_LOOKOUT_EMAIL_AFTER` says. It is off unless you start it with `AGENT_LOOKOUT_EMAIL_TO` and `AGENT_LOOKOUT_SMTP_URL`, and by default it sends nothing anywhere. Once set up, it sends one short plain-text email for each wait, through the mail server you name, to the one address you name, over TLS, at most 20 in an hour. The Email card in Settings says whether it is on and how the last email went.
- `AGENT_LOOKOUT_EMAIL_EVENTS` chooses what is emailed: any of `needs-you`, `finished`, `failed` and `ended`, separated by commas. It is `needs-you` unless you set it. A session that finishes, fails or ends is emailed at once, within the same 20 an hour, with a subject such as "billing-webhooks finished". The Email card names the events it sends.
- Agent Lookout can post to a webhook, such as a Slack channel's incoming webhook, when a session has waited for you for a minute, or as long as `AGENT_LOOKOUT_WEBHOOK_AFTER` says, and, with `AGENT_LOOKOUT_WEBHOOK_EVENTS`, when one finishes, fails or ends. It is off unless you start it with `AGENT_LOOKOUT_WEBHOOK_URL`, and by default it sends nothing anywhere. Once set, it sends one short JSON post for each, to that one address and no other, over HTTPS, at most 20 in an hour, counted apart from emails. Each post names the session, what happened and when, and its folder's name, app and agent, and nothing in a session's name can mention someone, ping a channel or make a link that shows other words than its address. A Slack incoming webhook takes the posts with nothing more to set up, and Discord takes them with `/slack` added to its address. The Webhook card in Settings says whether it is on, names the host alone and says how the last post went.

#### Sources, Settings and the page

- A rail down the left edge moves between the Overview, Sources and Settings, and its mark lights up while any session needs you.
- The browser tab's title shows how many sessions need you, so it can be read while the tab is in the background.
- The Sources view says whether Claude Code and Codex were found, what Agent Lookout reads and runs for each, and how often. A card for status files says whether their folder is there, how often it is read, and how many files were read and skipped.
- Under the source cards, What each agent can report says Yes, No or Partly for each agent and each thing it can show, such as needs you, finished, Jump and quiet for, with the reason for each No and Partly. The guide has the same table.
- Night and Day themes: panels of tinted glass over a warm black at Night or a warm stone by Day, with amber kept for the sessions that need you. Settings can make the theme follow the computer's setting.

#### Outside the dashboard

- `npm run build` followed by `npm start` serves the dashboard from one local process at `127.0.0.1:4777`.
- `agent-lookout`, or `agent-lookout start`, starts Agent Lookout as `npm start` does and prints its address. `--port` chooses the port, and `--open` opens the address in the default browser. The package for npm holds the built dashboard and the command as plain JavaScript, so `npx agent-lookout` runs it with nothing to clone and no TypeScript. It also holds `dist/THIRD-PARTY-LICENSES.md`, with the licences of the libraries and fonts the dashboard includes.
- `agent-lookout --version`, or `-v`, prints the version.
- `agent-lookout status` prints in the terminal which sessions need you: the counts, then each waiting session's name, the reason and how long it has waited. `--count` prints only the number, for a tmux status line or a shell prompt, and `--json` prints the same as JSON. The exit code is 0 when nothing needs you, 1 when a session does and 2 when it cannot tell, such as when Agent Lookout could not be reached or read. It reads the Agent Lookout already running on this machine, at a loopback address only, and starts nothing. Run it with `npx agent-lookout status`, as `agent-lookout status` after `npm install -g agent-lookout`, or in a clone with `npm run --silent status`.
- `agent-lookout mcp` lets an AI agent keep track of your other agents. It is a Model Context Protocol server that the agent's app starts and speaks to over stdin and stdout, so it listens on no port, and it reads the Agent Lookout already running on this machine, at a loopback address only, as `agent-lookout status` does. Its three tools only read: `list_sessions` gives every session with its status, the reason it waits, its folder's name, branch, app and how long it has been quiet, or only those with one status; `sessions_needing_you` gives the waits, longest first, with how long each has waited and one sentence that sums them up; and `sources` says whether each agent is being read and what it can and cannot report. Each tool says that session names are untrusted text written by other programs, and anything a terminal would act on, and any character that shows nothing, is taken out of them. When Agent Lookout is not running, each tool says so and how to start it. Add it to Claude Code with `claude mcp add agent-lookout -- npx -y agent-lookout mcp`, or in a clone with `<path to the clone>/bin/agent-lookout.mjs mcp` in place of `npx -y agent-lookout mcp`.
- docs/API.md describes the local API: every route and its answer, the `Host` and `Origin` rules, the notifications header and the checks on `POST /api/jump`. The API is for this machine only, and has no token.

#### On Linux

- Agent Lookout runs on Linux, started the same way and reading the same folders. It has been checked in CI on Ubuntu by starting it with `npm start` and reading back its sessions, and not yet by a person on a Linux desktop. The guide's On Linux part says what works there.
- When it is not on `PATH`, the `claude` command is also looked for in `~/.npm-global/bin` and `/usr/bin`, after the places it was looked for on a Mac.
- A Claude Code session whose start time `ps` now gives up to a minute away from the one in its registry file is still shown. Linux's `ps` gives another start time after the clock is set, as it often is after waking from sleep.
- Notifications with no dashboard tab open, and Jump to a tab of Terminal or iTerm2, are macOS only. Started with `AGENT_LOOKOUT_NOTIFICATIONS=on` anywhere else, Agent Lookout prints a line saying it shows no notifications itself.
